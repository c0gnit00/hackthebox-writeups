## Executive Summary

This report documents the full security assessment, technical breakdown, and complete compromise of **Garfield**, an Active Directory environment operating under the domain `garfield.htb`. The assessment was initiated under an **Assumed Breach** scenario, where initial low-privileged domain credentials for `GARFIELD\j.arbuckle` (`Th1sD4mnC4t!@1978`) were provided.

The path to full domain compromise relies on a complex chain of delegated Active Directory permissions, SYSVOL file system access misconfigurations, and Read-Only Domain Controller (RODC) control-plane architecture weaknesses:

1. **Assumed Breach & Domain Enumeration:** Valid domain credentials for `GARFIELD\j.arbuckle` confirm access to SMB, LDAP, and RPC on the primary Domain Controller `DC01.garfield.htb` (Windows Server 2019).
2. **`WriteScriptPath` ACL Abuse & SYSVOL Misconfiguration:** Enumeration via `bloodyAD` reveals that `j.arbuckle` possesses `WriteProperty` rights over the `scriptPath` LDAP attribute for both `l.wilson` and `l.wilson_adm`. Furthermore, the `IT Support` group (of which `j.arbuckle` is a member) holds Modify permissions on the SYSVOL scripts directory (`C:\Windows\SYSVOL\sysvol\garfield.htb\scripts`).
3. **Logon Script Execution & Account Reset:** A custom batch file (`Script.bat`) is placed in the SYSVOL scripts directory and configured as the logon script for `l.wilson`. When executed in `l.wilson`'s security context, the script abuses `l.wilson`'s `ForcePasswordChange` permission over `l.wilson_adm` to reset `l.wilson_adm`'s password to `P@ssw0rd123!`.
4. **Internal Network Pivoting & RODC Discovery:** Authenticating as `l.wilson_adm` via WinRM on `DC01` exposes a secondary internal network adapter (`192.168.100.0/24`). A ping sweep discovers an internal Read-Only Domain Controller (`RODC01.garfield.htb`) at `192.168.100.2`. A Ligolo-ng reverse tunnel is established to route traffic into the internal subnet.
5. **RODC Group Membership & Attribute Abuse:** BloodHound graph analysis shows `l.wilson_adm` is a member of `Tier 1`, which has rights to add accounts to `RODC Administrators`. Adding `l.wilson_adm` to `RODC Administrators` grants full write access over the `RODC01$` computer object. Using `bloodyAD`, the `managedBy` attribute on `RODC01$` is assigned to `RODC Administrators`, granting local administrative rights on `RODC01`.
6. **RODC Password Replication Policy (PRP) Manipulation:** With write access over `RODC01$`, the `msDS-RevealOnDemandGroup` attribute is modified to include `Domain Admins`, `Domain Controllers`, and `Domain Users`, while the explicit deny-list `msDS-NeverRevealGroup` is cleared.
7. **RODC Key Extraction & Kerberos Keylist Attack:** Connecting to `RODC01` via WinRM as `l.wilson_adm`, Mimikatz dumps the AES-256 secret key for the RODC's linked Kerberos account (`krbtgt_8245`). Using Rubeus, a Golden Ticket is forged for `administrator` using the `krbtgt_8245` AES-256 key and submitted in a `KERB-KEY-LIST-REQ` TGS request to `DC01`. Because `Administrator` is allowed by the modified PRP, `DC01` returns the NT password hash for `Administrator` (`EE238F6DEBC752010428F20875B092D5`).
8. **Domain Administrator Compromise:** Authenticating via Pass-the-Hash with Evil-WinRM as `GARFIELD\Administrator` grants full Administrative control over `DC01` and the entire `garfield.htb` forest.

## Active Directory Vulnerability & Concept Deep-Dive

Before proceeding with exploitation, it is essential to review the core Active Directory mechanisms and misconfigurations exploited in this attack path.

### 1. `scriptPath` Attribute & `WriteScriptPath` Abuse Mechanics

A **logon script** is a batch (`.bat`, `.cmd`) or VBScript file that Active Directory automatically executes on a client machine whenever a domain user initiates an interactive or desktop session. Logon scripts are commonly deployed to map network drives, synchronize host clocks, or install software.

The **`scriptPath`** LDAP attribute (`CN=Script-Path`, schema GUID `bf9679a8-0de6-11d0-a285-00aa003049e2`, covered under Property Set GUID `5f202010-79a5-11d0-9020-00c04fc2d4cf`) stores the relative filename of the user's logon script.

While the attribute stores only the file name (e.g. `Script.bat`), Windows client systems fetch and execute the file from a designated Domain Controller path:
- **Physical Path on DC:** `C:\Windows\SYSVOL\sysvol\<domain_name>\scripts\`
- **Network Share Path:** `\\<domain_name>\netlogon\` or `\\<domain_name>\sysvol\<domain_name>\scripts\`

**The Vulnerability / Abuse Vector:**
If a non-privileged principal possesses `WriteProperty` permissions over a target account's `scriptPath` attribute AND has write permissions to the `SYSVOL\scripts` directory, an attacker can:
1. Upload a custom batch file (`Script.bat`) into `SYSVOL\scripts\`.
2. Update the target user's `scriptPath` attribute to point to `Script.bat`.
3. When the target user logs in or authenticates, the Domain Controller instructs the client host to execute `Script.bat` in the security context of the target user.

On modern Windows OS builds (Windows 8.1+), Group Policy introduces a default **5-minute delay** before executing logon scripts to optimize desktop boot times (`Configure Logon Script Delay`). Unless explicitly disabled or overridden, attackers must allow up to 5 minutes (or trigger interactive logons) for script execution.

For detail insight read this [blog](https://medium.com/@muneebnawaz3849/writescriptpath-abuse-in-active-directory-cb5945848a51) by Furious-05

### 2. Read-Only Domain Controllers (RODCs) & Password Replication Policies

A **Read-Only Domain Controller (RODC)** is a Domain Controller that hosts a read-only copy of the Active Directory database (`ntds.dit`). RODCs are typically deployed in branch offices or physically insecure locations where local authentication is required, but full Domain Controller physical security cannot be guaranteed.

Unlike standard writable DCs, RODCs feature key security controls and unique attack surface considerations:

1. **Unidirectional Replication:** Changes to AD objects cannot be made directly on an RODC; all directory updates originate on writable DCs (`DC01`) and replicate inbound to the RODC.
2. **Password Replication Policy (PRP):** To prevent domain-wide credential exposure if an RODC is physically compromised, RODCs do NOT store domain user password hashes by default. Credential caching is controlled by two Active Directory attributes on the RODC computer object:
   - **`msDS-RevealOnDemandGroup` (Allow-list):** Specifies principals (users, groups, computers) whose password hashes are permitted to be cached on the RODC when they authenticate through it.
   - **`msDS-NeverRevealGroup` (Deny-list):** Explicitly forbids credential caching for high-value principals (e.g. `Domain Admins`, `Enterprise Admins`, `Administrators`, `krbtgt`). **The deny-list always overrides the allow-list.**
3. **Dedicated RODC KRBTGT Account (`krbtgt_XXXXX`):** Each RODC in a domain is provisioned with a unique, dedicated Kerberos account (e.g. `krbtgt_8245`, where `8245` is the `msDS-SecondaryKrbTgtNumber`). When a user authenticates locally against an RODC, the RODC issues a TGT encrypted with its own `krbtgt_XXXXX` key rather than the main domain `krbtgt` key.
4. **RODC `managedBy` Administrative Delegation:** Local administrative control of a standard DC is governed by Domain/Enterprise Admins groups. On an RODC, local administrator rights are granted directly to the security principal defined in the computer object's **`managedBy`** attribute.

For detail insight read this [blog](https://specterops.io/blog/2023/01/25/at-the-edge-of-tier-zero-the-curious-case-of-the-rodc/) by Elad Shamir and this [blog](https://adsecurity.org/?p=3592) by Sean Metacalf  

### 3. Kerberos Keylist Attack Mechanics

The **Kerberos Keylist Attack** (originally conceptualized by 0xdeaddood and implemented in tools like Rubeus) exploits RODC architecture to compromise domain accounts:

1. Writable Domain Controllers (`DC01`) maintain a specialized RPC endpoint (**DRSUAPI / `KERB-KEY-LIST-REQ`**) that allows an RODC to request account credentials (NT hashes / Kerberos keys) for users permitted by its Password Replication Policy.
2. When an RODC requests credentials for a user, `DC01` evaluates the RODC's `msDS-RevealOnDemandGroup` and `msDS-NeverRevealGroup` attributes.
3. If an attacker gains control over an RODC object (e.g. via `managedBy` or group ACLs), the attacker can:
   - Modify `msDS-RevealOnDemandGroup` to include Tier-0 accounts like `Administrator` or `Domain Controllers`.
   - Clear `msDS-NeverRevealGroup` to remove explicit protections.
   - Extract the RODC's `krbtgt_XXXXX` AES-256 key from local memory/LSA secrets.
   - Forge a Golden Ticket for `Administrator` signed by `krbtgt_XXXXX` (including the RODC key version number `/rodcNumber`).
   - Submit a `KERB-KEY-LIST-REQ` TGS request to `DC01`. Because `Administrator` is now explicitly permitted by `msDS-RevealOnDemandGroup`, `DC01` fulfills the request and returns the decrypted NT hash of the `Administrator` account!

For detail insight read this [blog](https://0xdeaddood.rocks/2021/11/11/the-kerberos-key-list-attack-the-return-of-the-read-only-domain-controllers/) by Leandro Cuozzo

### Modifying RODC Password Replication Policy (PRP)

## Remediation & Security Recommendations

To address the security flaws identified during this assessment and prevent future compromise, the following remediation measures are recommended:

1. **Remove Delegated `WriteProperty` Rights on `scriptPath` [Critical]:** Audit Object Access Control Lists (ACLs) across Active Directory users and remove delegates with `WriteProperty` rights over sensitive user attributes like `scriptPath` and `profilePath`. Implement least privilege access model for helpdesk accounts.
2. **Restrict SYSVOL Folder File Permissions [High]:** Modify NTFS file permissions on `C:\Windows\SYSVOL\sysvol\<domain>\scripts` to ensure non-administrative user groups (such as `IT Support`) do not hold Modify (`M`) or Write (`W`) access. Only designated Domain Administrators should be permitted to upload or modify logon scripts.
3. **Audit RODC Object Permissions & Password Replication Policies [Critical]:**
   - Restrict write permissions on RODC computer objects to Tier-0 Domain Administrators only. Prevent intermediate support groups (like `Tier 1` or `RODC Administrators`) from modifying critical attributes (`managedBy`, `msDS-RevealOnDemandGroup`, `msDS-NeverRevealGroup`).
   - Maintain a strict explicit deny-list (`msDS-NeverRevealGroup`) containing all Tier-0 principals (`Domain Admins`, `Enterprise Admins`, `Administrators`, `krbtgt`). Never add administrative accounts or broad groups (`Domain Users`, `Domain Controllers`) to `msDS-RevealOnDemandGroup`.
4. **Reduce Machine Account Quota (MAQ) [High]:** Lower Active Directory's default `ms-DS-MachineAccountQuota` attribute from `10` to `0` across the domain to prevent unprivileged accounts from creating new computer objects for Resource-Based Constrained Delegation (RBCD) attacks.
5. **Monitor & Audit Logon Script Modifications [Medium]:** Enable Directory Service Changes Auditing (Event ID 5136) to detect modifications to user `scriptPath` attributes. Monitor file creation and modification events within the SYSVOL scripts directory (Event ID 4663 / 4688).
