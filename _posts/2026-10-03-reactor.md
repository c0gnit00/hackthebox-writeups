## Executive Summary

This writeup documents the complete attack chain against the HackTheBox machine **Reactor**, a Linux system running a vulnerable Next.js application.

**Attack Chain Summary:**

1. **React Flight Deserialization (CVE-2025-55182) -> Initial Access:** Enumeration of the web application on port 3000 revealed it was built with Next.js 15.0.3 and React 19.0.0. These versions are vulnerable to CVE-2025-55182, a deserialization flaw in the React Flight protocol. A malicious multipart form request was crafted to bypass object property validation, injecting a reverse shell payload that executed within the Node.js context as the `node` user.
2. **Database Credential Extraction -> Lateral Movement:** Local enumeration identified a SQLite database (`reactor.db`) accessible to the `node` user. Querying the `users` table yielded an MD5 password hash for the user `engineer`. The hash was successfully cracked using John the Ripper to reveal the plaintext password (`reactor1`), which was used to establish an interactive SSH session.
3. **Node.js V8 Inspector Exploitation -> Root:** System enumeration revealed a background Node.js process (`/opt/uptime-monitor/worker.js`) running as `root` with the V8 Inspector debugging protocol enabled on localhost port 9229 (`--inspect=127.0.0.1:9229`). An SSH local port forward was established to access the debugger. The `wscat` utility was then used to interact with the WebSocket endpoint, executing arbitrary JavaScript via `Runtime.evaluate` to spawn a reverse shell as `root`.

### CVE-2025-55182: React Flight Deserialization Vulnerability

#### Vulnerability Overview

The target environment exhibits vulnerability to [CVE-2025-55182](https://react2shell.com/), a critical remote code execution flaw affecting React Server Components (RSC) implementations. This vulnerability impacts Next.js versions 15.0.0 through 16.0.6 and React RSC versions 19.0.0 through 19.2.0. Technical details are derived from [Trend Micro's comprehensive analysis](https://www.trendmicro.com/en_us/research/25/l/CVE-2025-55182-analysis-poc-itw.html).

#### React Server Components Architecture

React Server Components represent a paradigm shift in full-stack web development, enabling component logic to execute exclusively on the server. This architectural pattern offers significant advantages:
- **Reduced client-side payload:** Only essential interactive components are sent to the browser
- **Direct backend access:** Server components can directly query databases and access secrets
- **Progressive rendering:** The server can stream UI updates to the client as they become available

To facilitate communication between server and client, Next.js implements `React Flight`, a specialized serialization protocol that encodes complex JavaScript data structures (component trees, promises, refs) into a streamable format.

#### React Flight Serialization Format

The Flight protocol uses special prefix markers (prefixed with `$`) to denote data types and facilitate deserialization:

| Prefix | Type | Purpose | Vulnerability Status |
|--------|------|---------|----------------------|
| `$@` | Raw chunk reference | References raw chunk data for deduplication | **Exploited** - allows prototype chain traversal |
| `$B` | Blob/Binary data | Transfers binary data and FormData objects | **Exploited** - provides RCE gadget chain |
| `$F` | Function reference | References server functions for client invocation | Standard / Low risk |
| `$L` | Lazy component | Marks components for deferred loading | Standard / Low risk |

#### Vulnerability Root Cause

The vulnerability resides in the `reviveModel` function within React's Flight deserialization code. The implementation contains a critical flaw in property ownership validation:

```javascript
// VULNERABLE CODE - ReactFlightReplyServer.js
for (i in value) {
    // Ownership check queries untrusted object itself
    value.hasOwnProperty(i) &&  // PROBLEM: attacker controls value!
    // ... process property
}
```

**Exploitation Chain Trigger:**
In JavaScript's prototype-based inheritance model, every object inherits methods from `Object.prototype`, including `hasOwnProperty()`. An attacker can inject a malicious `hasOwnProperty` function into the controlled object, effectively bypassing the ownership check and exposing the entire prototype chain including:
- `__proto__` - The prototype chain itself
- `constructor` - Reference to Function constructor
- Other internal object properties

#### Four-Stage Exploitation Chain

The complete exploitation process involves four distinct stages that progressively escalate privileges and inject malicious code:

##### Stage 1: Prototype Chain Traversal via Circular References

The attacker establishes a circular reference pattern using the `$@` prefix to create a self-referential loop:

```json
{
  "0": "{\"callback\": \"$1:__proto__:then\"}",
  "1": "\"$@0\""
}
```

**Explanation:** 
- Chunk 0 references chunk 1 via `$1`
- Chunk 1 contains a raw reference back to chunk 0 via `$@0`
- By traversing `$1:__proto__:then`, the attacker gains access to prototype chain methods
- The colon-separated path allows navigation through object properties and prototypes

This creates a traversal path to reach the Function constructor: `$1:__proto__:constructor:constructor`

##### Stage 2: JavaScript Promise Mechanism Hijacking

The attacker injects a malicious `then` method that hijacks JavaScript's `await` operator:

```javascript
// Attacker's malicious then implementation
Chunk.prototype.then = function(resolve, reject) {
    if (this.status === "resolved_model") {
        initializeModelChunk(this);  // Triggered by the attacker
    }
};
```

**Technical Details:**
- JavaScript's `await` operator automatically invokes `.then()` on any object with that method (duck typing for Promise detection)
- By replacing `then` on the internal `Chunk` object, the attacker forces React to process attacker-controlled data
- The `initializeModelChunk()` function is designed to parse and trust the chunk's `.value` field

##### Stage 3: Malicious Data Injection During Model Initialization

The attacker crafts a payload that triggers the chunk initialization with attacker-controlled data:

```javascript
function initializeModelChunk(chunk) {
    var rawModel = JSON.parse(chunk.value);  // attacker-controlled
    // React trusts this data completely
}
```

By setting `status: "resolved_model"` and providing a `.value` field containing:
```json
{"then": "$B1337"}
```

The attacker instructs React to process a Blob handler (`$B` prefix) during deserialization.

##### Stage 4: Remote Code Execution via Blob Handler

The `$B` prefix triggers React's blob handling code:

```javascript
case "B":  // Blob handler
    return response._formData.get(response._prefix + obj);
    // Becomes: Function("require('child_process').execSync('malicious-command');//0")()
```

**Exploitation Mechanism:**
- The attacker controls `_formData.get` by pointing it to the Function constructor
- The `_prefix` field contains arbitrary JavaScript code
- React concatenates `_prefix` with a chunk ID, then passes this to the Function constructor
- The JavaScript comment `//` at the end neutralizes the chunk ID suffix
- The Function constructor executes the injected code with full Node.js process privileges

### Privilege Escalation to Root: Node.js V8 Inspector Protocol Exploitation

#### Overview: Node.js Debugger as Privilege Escalation Vector

The Node.js runtime supports remote debugging via the V8 Inspector Protocol, an interface compatible with Chrome DevTools and other debugging clients. When exposed without proper access controls, this protocol provides a direct method for arbitrary code execution within the Node.js process context, inheriting all process privileges.

### Why This Escalation Works: Security Analysis

1. **No Authentication:** The V8 Inspector Protocol lacks built-in authentication/authorization
2. **Full Code Execution:** The `Runtime.evaluate` method executes arbitrary JavaScript
3. **Process Privilege Inheritance:** Code executed via the debugger runs with the process's UID (root in this case)
4. **Local Network Assumption:** The developers assumed only trusted local users could access port 9229; however, lateral movement to the `engineer` user violated this assumption

## Mitigations & Recommendations

### 1. Upgrade Next.js and React — Remediate CVE-2025-55182

**Action:** Upgrade the Next.js and React frameworks to patched versions. For Next.js 15, upgrade to 15.0.7 or later (or 14.2.23 if on the 14.x branch). Upgrade React to 19.0.0-rc.1 or later.

```bash
# Update package dependencies
npm install next@latest react@latest react-dom@latest
```

**Root Cause:** The application was running Next.js 15.0.3 and React 19.0.0, which contain a critical vulnerability (CVE-2025-55182) in the React Server Components (RSC) Flight deserializer. The `reviveModel` function incorrectly trusted the prototype chain of user-supplied objects, allowing attackers to inject malicious blob handlers and execute arbitrary code.

---

### 2. Implement Strong Password Policies and Hashing Algorithms

**Action:** Replace weak MD5 hashing with a modern, computationally expensive password hashing algorithm such as bcrypt, Argon2, or scrypt. Additionally, enforce strong password complexity requirements for all users.

```javascript
// Example using bcrypt for secure password hashing in Node.js
const bcrypt = require('bcrypt');
const saltRounds = 12;
const hash = await bcrypt.hash(plaintextPassword, saltRounds);
```

**Root Cause:** User credentials in `reactor.db` were hashed using MD5 without a salt, a weak hashing algorithm vulnerable to fast dictionary attacks. The `engineer` account also used a weak, easily guessable password (`reactor1`), allowing rapid offline cracking.

---

### 3. Restrict Access to Sensitive Databases

**Action:** Ensure that the web application runs with the principle of least privilege. If the Node.js application requires access to the database, store it in a directory with strict permissions that prevent other system users or compromised web services from exfiltrating the entire database file.

```bash
# Set strict permissions on the database file
chmod 600 /opt/reactor-app/reactor.db
chown <application_user>:<application_group> /opt/reactor-app/reactor.db
```

**Root Cause:** The `reactor.db` file was readable by the `node` user, allowing an attacker who compromised the web application to extract the database contents, including other users' credentials.

---

### 4. Disable Node.js Debugging (V8 Inspector) in Production

**Action:** Remove the `--inspect` or `--inspect-brk` flags from Node.js startup commands in production environments. Debugging protocols should only be enabled in secure development or staging environments.

```bash
# BAD: Starting Node.js with the inspector enabled
node --inspect=127.0.0.1:9229 /opt/uptime-monitor/worker.js

# GOOD: Starting Node.js normally
node /opt/uptime-monitor/worker.js
```

**Root Cause:** A root-privileged Node.js process was started with the V8 Inspector protocol enabled on localhost. The protocol provides unauthenticated, full remote code execution capabilities by design. An attacker who gained local access as a standard user (`engineer`) was able to tunnel to this port and execute arbitrary code as `root`.
