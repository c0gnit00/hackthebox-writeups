## Executive Summary

Fries is a Hard-rated hybrid Windows/Linux HackTheBox machine that chains web application vulnerabilities, Linux privilege escalation, and Active Directory Certificate Services (ADCS) abuse into a complete domain compromise.

The attack path proceeds as follows:

1. **Gitea Source Code Exposure** — Provided credentials allow login to a self-hosted Gitea instance. Inspecting commit history reveals hardcoded PostgreSQL credentials pointing to an internal database management service.

2. **CVE-2025-2945 (pgAdmin 4 RCE)** — The internal `db-mgmt05.fries.htb` host runs pgAdmin 4 v9.1.0, which is vulnerable to an authenticated Remote Code Execution vulnerability. Using the Metasploit module, a Meterpreter shell is obtained inside the pgAdmin Docker container.

3. **NFS GID Impersonation — Root on Linux Host** — A Docker environment variable leaks an SSH password. Password spraying identifies valid credentials for the `svc` user on the Linux host. The NFS export at `/srv/web.fries.htb` uses UID/GID mapping without full squashing. By impersonating GID 6 (the `disk` group) on the attack machine and placing a `setgid` static bash binary on the NFS share, code execution with effective `disk` group membership is achieved. This allows reading block devices directly with `debugfs`, revealing root's SSH private key and the user flag.

4. **Docker Authorization Plugin Bypass** — The Docker daemon is exposed over TLS on port 2376 and uses the `authz-broker` authorization plugin. The NFS `certs` directory contains the CA key, which is used to generate a valid client certificate for the `sysadm` user. This bypasses the authorization plugin and grants Docker API access.

5. **PWM LDAP Credential Theft** — A running PWM password self-service container is dumped via `docker cp`. Its configuration file contains a bcrypt hash for the admin password, which is cracked. Logging into PWM's configuration editor and redirecting the LDAP bind URL to a Responder listener captures cleartext credentials for `svc_infra`.

6. **ADCS ESC6/ESC7/ESC16 — Domain Admin** — BloodHound reveals `svc_infra` can read the `gMSA_CA_prod$` managed password. This gMSA account holds `ManageCA` rights over the domain Certificate Authority, enabling ESC7. After ESC7's `SubCA` template request fails due to ACL restrictions, the CA is configured to enable User Specified SAN (ESC6) and disable the NTDS Security Extension (ESC16). A certificate is then requested for `administrator@fries.htb`, yielding the Administrator NT hash and full domain compromise.

**Impact:** Complete compromise of the Linux host and the `fries.htb` Active Directory domain. All domain credentials are accessible via DCSync.

The scan reveals an unusual combination of services that immediately defines the attack surface:

## Exploiting pgAdmin 4 — CVE-2025-2945

The virtual host `db-mgmt05.fries.htb` hosts a pgAdmin 4 database management interface. pgAdmin is a widely used open-source web tool for managing PostgreSQL databases.

<img src="assets/img/fries/pgadmin4.png" alt="error loading image">

<img src="assets/img/fries/pgadmin4_about.png" alt="error loading image">

The running version is **pgAdmin 4 v9.1.0**, which is affected by **CVE-2025-2945** — an authenticated Remote Code Execution vulnerability. The vulnerability exists in the Query Tool feature, which allows arbitrary SQL to be executed against a connected database server. pgAdmin's backend exposes internal APIs that process SQL queries, and a flaw in the way user-supplied input is handled allows an authenticated user to escape the query context and execute system-level commands on the underlying server. Since pgAdmin runs as the `pgadmin` OS user inside a container, successful exploitation yields a shell in the containerized environment.

## Exploiting NFS Permissions and GID Impersonation

NFS relies on the client's reported UID and GID for access control. When `root_squash` is enabled (the common default), root on the client is mapped to `nobody`, but all other UIDs and GIDs are trusted as-is. This means that if we run a process on the attack machine with GID 59605603, the NFS server will treat it as a member of the `infra managers` group and allow access to the `certs` directory.

### Escalating to Root on the Linux Host

The TLS keys are set aside for later. For now, we focus on gaining root on the Linux host.

On Linux, the `disk` group (GID 6) has read and write access to raw block devices (e.g., `/dev/sda`, `/dev/mapper/*`). This is a legacy permission model that predates modern filesystem namespacing. A process with effective GID 6 can open block devices directly, bypassing all filesystem-level ACL and permission checks — because it talks to the block layer below the filesystem.

The NFS server preserves GID values for non-root users. So if we run a process on the attack machine with GID 6 and place a file on the NFS `shared` directory (which is world-writable), the server sees that file as owned by GID 6 (the `disk` group). We can set the `setgid` bit on a binary placed there, so when `svc` runs it on the host, the process inherits effective GID 6 — without `svc` ever being a member of the `disk` group.

We start a Python shell with root to set GID 6 on the attack machine:

```shell
kalikali$ sudo python3
Python 3.13.9 (main, Oct 15 2025, 14:56:22) [GCC 15.2.0] on linux
Type "help", "copyright", "credits" or "license" for more information.
>>> import os
>>> os.setgid(6)
>>> os.system("/usr/bin/bash")
rootkali$ id
uid=0(root) gid=6(disk) groups=6(disk),0(root)
```

Now running as root with GID 6 (disk), we mount the NFS share. Files we create will appear on the server as owned by GID 6.

```shell
rootkali$ sudo mount -t nfs 172.18.0.1:/srv/web.fries.htb /mnt/nfs
```

We place a statically compiled bash binary (which does not depend on system libraries, so it works on any Linux host) into the `shared` directory and set the `setgid` bit. The `setgid` bit on an executable causes it to run with the file's group permissions rather than the caller's group. Since the file is owned by GID 6 (`disk`), running it from `svc`'s session will give an effective GID of 6.

## Docker Authorization Plugin Bypass and PWM Container Access

The Docker daemon is secured by two layers: filesystem permissions on the local socket (`/var/run/docker.sock`), and the `authz-broker` authorization plugin for the TLS API.

- `svc` is not in the `docker` group, so it cannot reach the local socket.
- `root` can reach the local socket, but the `authz-broker` plugin has no policy entry matching root's `container_list` action — it rejects the request.

This creates a deadlock on the local socket path. However, the daemon also exposes a TLS-authenticated API on `127.0.0.1:2376`. Any client presenting a valid certificate signed by the Docker CA can use this API, and the `authz-broker` plugin evaluates the CN (Common Name) of the client certificate against its policy file.

We inspect the policy file to understand what is permitted:

```shell
svc@web:~$ docker ps
permission denied while trying to connect to the Docker daemon socket at unix:///var/run/docker.sock: Get "http://%2Fvar%2Frun%2Fdocker.sock/v1.50/containers/json": dial unix /var/run/docker.sock: connect: permission denied
```

```shell
root@web:~# docker ps
Error response from daemon: authorization denied by plugin authz-broker: no policy applied (user: '' action: 'container_list')
```

Checking the authorization plugin's policy file:

```shell
svc@web:~$ cat /var/lib/authz-broker/policy.json
{"name":"policy_1", "users": ["svc"], "actions": ["container_list", "container_logs"]}
{"name":"policy_1", "users": ["sysadm"], "actions": ["container"], "readonly":true}
{"name":"policy_2", "users": ["root"], "actions": [""]}
```

The policy is:
- `svc` may `container_list` and `container_logs` — but `svc` has no OS-level access to the socket.
- `sysadm` may any `container` action in read-only mode.
- `root` has an empty actions list — effectively no policy, causing the plugin to reject everything.

The winning path is: generate a TLS client certificate with CN=`sysadm`, sign it with the Docker CA (whose key we extracted from the NFS `certs` directory), and use it to authenticate to the TLS API on port 2376. The `authz-broker` plugin will see CN=`sysadm` and permit `container` read-only actions — which includes listing containers, inspecting them, and copying their filesystems.


We pivot to a two-part alternative using **ESC6** and **ESC16**:

**ESC6** — When the CA has the `EDITF_ATTRIBUTESUBJECTALTNAME2` flag set in its policy module, any authenticated enrollee can specify an arbitrary Subject Alternative Name (SAN) on any certificate request, regardless of template settings. This means we can request a standard `User` template certificate (which we are allowed to enroll for) and specify `administrator@fries.htb` as the SAN, effectively impersonating the Domain Administrator.

**ESC16** — The NTDS Security Extension (OID `1.3.6.1.4.1.311.25.2`) embeds the requestor's domain SID into issued certificates, allowing the domain to verify that the certificate holder's SID matches the account's actual SID. When this extension is globally disabled on the CA, that SID binding check is skipped, making it possible to impersonate high-privilege accounts with a certificate that does not carry their actual SID.

With `ManageCA` rights, `gMSA_CA_prod$` can write CA registry settings remotely. We use Evil-WinRM to authenticate and run a PowerShell script that:
1. Sets the `EDITF_ATTRIBUTESUBJECTALTNAME2` flag (ESC6 — enables user-supplied SAN)
2. Adds OID `1.3.6.1.4.1.311.25.2` to `DisableExtensionList` (ESC16 — disables SID extension globally)
3. Restarts the Certificate Services to apply both changes

- [ESC16 — Security Extension Disabled](https://www.hackingarticles.in/adcs-esc16-security-extension-disabled-on-ca-globally/)

We execute a PowerShell script using the `PSPKI` module to enable User Specified SAN (ESC6) and disable NTDS security extensions (ESC16).

```shell
 # Load the PSPKI module to manage AD CS via PowerShell
Import-Module PSPKI

# Define the Certification Authority hostname
$CAName = "dc01.fries.htb"

# Path to the CA policy registry node
$policyPath = "PolicyModules\CertificateAuthority_MicrosoftDefault.Policy"

# Create an object to read/write CA configuration
$configReader = New-Object SysadminsLV.PKI.Dcom.Implementations.CertSrvRegManagerD $CAName

# Set configuration access to the root registry node
$configReader.SetRootNode($true)

# Read the current EditFlags value from the CA policy
$currentEditFlags = $configReader.GetConfigEntry("EditFlags", $policyPath)

# Add the SAN flag (0x40000) to allow editing SAN in requests
$newEditFlags = $currentEditFlags -bor 0x40000

# Write the updated EditFlags back to the CA policy
$configReader.SetConfigEntry($newEditFlags, "EditFlags", $policyPath)

# Define OID for NTDS Security extension (SID extension)
$esc16OID = "1.3.6.1.4.1.311.25.2"

# Remove ESC16 behavior by disabling the extension in CA config         
$configReader.SetConfigEntry($esc16OID, "DisableExtensionList", $policyPath) 

# Restart Certificate Services to apply the configuration changes
Restart-Service -Name CertSvc -Force
```

## Mitigations & Security Recommendations

1. **Protect Git Secrets**: Implement pre-commit hooks and automated scanning (e.g., GitGuardian, Trufflehog) to prevent API keys, database credentials, and certificates from being committed to source repositories.
2. **Upgrade pgAdmin**: Ensure pgAdmin 4 is updated to version 9.2 or later to mitigate the authenticated RCE vulnerability (CVE-2025-2945).
3. **Secure NFS Exports**: Do not export directories with generic wildcards (`*`). Implement `root_squash` and `all_squash` configurations where appropriate, and restrict export access to specific host IP addresses.
4. **Harden Docker Socket Access**: Avoid running the Docker daemon with insecure authorization configurations. Limit access to `/var/run/docker.sock` to trusted administrative users. If using authorization plugins, ensure policies are strictly audit-controlled and cannot be bypassed via client-side certificate generation.
5. **Enforce LDAPS**: Configure web applications and internal services to use secure LDAP (LDAPS) with mandatory TLS certificate verification to prevent credential leakage via rogue LDAP server redirections.
6. **Harden Active Directory Certificate Services (AD CS)**:
   - Ensure the `EDITF_ATTRIBUTESUBJECTALTNAME2` flag is disabled on the CA to prevent ESC6 vulnerabilities.
   - Enforce strong certificate template ACLs, ensuring that low-privileged or service accounts do not possess `ManageCA` or `ManageCertificates` rights.
   - Retain the NTDS Security Extension (SID mapping extension) globally to prevent domain impersonation attacks (ESC16).
