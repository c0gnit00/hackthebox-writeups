## Executive Summary

Pirate is a hard-difficulty Active Directory machine running Windows Server 2019 that serves as the Domain Controller for the `pirate.htb` domain. The assessment begins with low-privileged domain credentials for the account `pentest`. Enumerating the Active Directory environment reveals that several computer accounts, including `MS01$` and `EXCH01$`, reside in the `Pre-Windows 2000 Compatible Access` group. Because these computer accounts were created with pre-Windows 2000 compatibility, they retain predictable default passwords matching their lowercase machine names (`ms01` and `exch01`), enabling an attacker to authenticate as `ms01$` and acquire a Kerberos Ticket Granting Ticket (TGT).

Further Active Directory analysis reveals that `MS01$` is a member of the `Domain Secure Servers` group, which holds read permissions over Group Managed Service Account (gMSA) passwords. Leveraging the `ms01$` Kerberos session, the managed password for `gMSA_ADCS_prod$` is retrieved from Active Directory. Because this service account belongs to the `Remote Management Users` group, an attacker can establish an interactive WinRM session on the Domain Controller. Internal network enumeration from `DC01` uncovers a dual-homed network configuration connecting to an isolated subnet, `192.168.100.0/24`. A host sweep identifies an active internal server at `192.168.100.2`. While `MS01$` and `EXCH01$` in the domain are merely pre-staged computer accounts with no real operating system or physical computer associated with them, Active Directory records confirm that `WEB01$` is the actual operational host on `192.168.100.2`.

A network pivot established via Ligolo-ng provides direct access to `WEB01`. While SMB signing is enforced on `DC01`, LDAP signing is not required and channel binding is disabled. The WebClient service is active on `WEB01`, opening an NTLM relay attack path. By creating an Active Directory integrated DNS record pointing to the attack platform and coercing authentication from `WEB01$` over WebDAV via PetitPotam (MS-EFSRPC), the incoming HTTP authentication is relayed to LDAP on `DC01`. The relay configures Resource-Based Constrained Delegation (RBCD) on `WEB01$` by granting delegation rights to a newly created computer account.

Using S4U2self and S4U2Proxy, a Kerberos service ticket is forged for the local Administrator account on `WEB01.pirate.htb`. Dumping LSA secrets from the server exposes a plaintext autologon password for the domain user `a.white`. Inspecting Access Control Lists reveals that `a.white` has `ForceChangePassword` rights over `a.white_adm`. This administrative account is configured with Constrained Delegation to `WEB01$` for the `HTTP` service class and holds `WriteSPN` permissions across all domain computers, including the Domain Controller `DC01$`. By removing the delegated SPN from `WEB01$` and re-registering it on `DC01$`, a Live SPN-jacking attack is executed. An S4U2Proxy request then generates a CIFS service ticket for `DC01$` impersonating the Domain Administrator, enabling a complete DCSync attack and dumping all domain credentials from `NTDS.DIT`.

### 2.3 Investigating Pre-Windows 2000 Compatible Accounts

The `Pre-Windows 2000 Compatible Access` group is a legacy built-in security group intended to allow older Windows NT 4.0 clients and servers to read user and group information across the domain. In Active Directory, when computer accounts are created with pre-Windows 2000 compatibility (characterized by the `userAccountControl` value 4128, which combines `WORKSTATION_TRUST_ACCOUNT` with `PASSWD_NOTREQD`), Active Directory sets their initial default password to the first 14 characters of the machine's account name in lowercase without the trailing dollar sign. Because these accounts were provisioned under this legacy standard and their passwords were never changed, they remain enabled with predictable default passwords (`ms01` for `MS01$` and `exch01` for `EXCH01$`).

While the BloodHound interface visually depicts `WEB01$` as part of this group, direct LDAP queries via `bloodyad` clarify the actual group membership.

Query the `member` attribute of the Pre-Windows 2000 Compatible Access group:

```shell
┌──(kali㉿kali)-[~/HTB/Machines/Pirate]
└─$ bloodyad -u 'pentest' -p 'p3nt3st2025!&' -d pirate.htb --host DC01.pirate.htb get object 'CN=PRE-WINDOWS 2000 COMPATIBLE ACCESS,CN=BUILTIN,DC=PIRATE,DC=HTB' --attr member

distinguishedName: CN=PRE-WINDOWS 2000 COMPATIBLE ACCESS,CN=BUILTIN,DC=PIRATE,DC=HTB
member: CN=EXCH01,CN=Computers,DC=pirate,DC=htb; CN=MS01,CN=Computers,DC=pirate,DC=htb; CN=DC01,OU=Domain Controllers,DC=pirate,DC=htb; CN=S-1-5-11,CN=ForeignSecurityPrincipals,DC=pirate,DC=htb
```

The LDAP directory confirms that only `EXCH01`, `MS01`, `DC01`, and `S-1-5-11` (Authenticated Users) belong to the group. `WEB01$` is not present in this group. Also `DC01$` account is not a Pre2k account, the UAC of `DC01$` does not contain `PASSWD_NOTREQD` flag.

## 3. Group Managed Service Account (gMSA) Abuse and Initial Foothold

### 3.1 Understanding gMSA Password Retrieval

Group Managed Service Accounts (gMSAs) are specialized domain accounts introduced in Windows Server 2012 that eliminate the need for administrators to manage service account passwords manually. The Active Directory Key Distribution Center generates a complex 128-byte cryptographically secure password for the gMSA and stores it in the `msDS-ManagedPassword` attribute of the gMSA object.

Access to calculate and retrieve this password blob is governed by the `msDS-GroupMSAMembership` attribute, which contains a security descriptor specifying the `PrincipalsAllowedToReadPassword`. Any security principal granted this right can query the domain controller over LDAP, retrieve the binary blob, and decode the current NTLM hash of the gMSA.

Inspecting `MS01$` in BloodHound reveals that it belongs to the `Domain Secure Servers` group.

<img src="assets/img/pirate/ms01_read_gmsa.png" alt="error loading image" width=100%>

The `Domain Secure Servers` group possesses permission to read the gMSA passwords for two service accounts: `GMSA_ADCS_PROD$` and `GMSA_ADFS_PROD$`.

Examining these service accounts in BloodHound demonstrates that both are members of the `Remote Management Users` group.

<img src="assets/img/pirate/remote_management_users.png" alt="error loading image" width=100%>

Membership in `Remote Management Users` grants the right to connect to any domain computer over Windows Remote Management (WinRM) on port 5985.

## 5. WebDAV Coercion and NTLM Relaying to LDAP

### 5.1 Analyzing the Relay Path

During initial reconnaissance on `DC01`, LDAP was enumerated with signing disabled (`signing:None`) and channel binding set to never (`channel binding:Never`). When LDAP signing and channel binding are not enforced, an attacker can relay incoming NTLM authentication to the LDAP service to modify Active Directory objects.

However, cross-protocol relaying from SMB to LDAP is blocked by modern Windows defenses: the NTLM Message Integrity Code (MIC) and SMB session binding mechanisms enforce signature verification when authenticating over SMB. Coercing an SMB connection from `WEB01` and attempting to forward it to LDAP will result in an authentication failure.

To bypass this barrier, authentication must be coerced over a protocol that does not enforce signing: HTTP. The Windows WebClient service implements the WebDAV protocol over HTTP. When WebClient initiates an outbound HTTP connection, the NTLM authentication header contains no signing requirements and can be cleanly relayed to an unsigned LDAP service.

### 5.2 Dynamic DNS Record Creation

## 6. Lateral Movement to WEB01$ and Credential Harvesting

### 6.1 Exploiting Resource-Based Constrained Delegation

Resource-Based Constrained Delegation (RBCD) allows the resource owner (in this case, `WEB01$`) to specify which accounts can delegate to it. With `YVSOJWBG$` recorded in `WEB01$`'s `msDS-AllowedToActOnBehalfOfOtherIdentity` attribute, `YVSOJWBG$` can leverage two Kerberos protocol extensions:

First, S4U2self (Service for User to Self) allows `YVSOJWBG$` to request a service ticket to itself on behalf of any domain user, such as `Administrator`.

### 7.2 The Mechanics of Live SPN-Jacking

Traditional exploitation of Constrained Delegation requires the attacker to compromise the account configured for delegation and then obtain service tickets to the target SPNs listed in `msDS-AllowedToDelegateTo`. If the target SPN points to a low-privilege service, the attack chain is limited unless the attacker holds the `SeEnableDelegation` privilege, which allows modifying `msDS-AllowedToDelegateTo` to point to higher-value targets. By default, `SeEnableDelegation` is held exclusively by Domain Admins.

However, as detailed in research by Elad Shamir, the restriction lies in the SPN definition, not the computer identity. When an account requests an S4U2Proxy service ticket for a target SPN like `HTTP/WEB01.pirate.htb`, the KDC queries Active Directory to locate which account owns that SPN, and encrypts the resulting service ticket with that account's secret key.

Because `a.white_adm` possesses `WriteSPN` rights over both `WEB01$` and `DC01$`, an attacker can manipulate the `servicePrincipalName` attributes:
First, remove `HTTP/WEB01.pirate.htb` from `WEB01$` to avoid duplicate SPN conflicts.
Second, add `HTTP/WEB01.pirate.htb` to `DC01$`.
Third, request an S4U2Proxy service ticket using `a.white_adm` for `HTTP/WEB01.pirate.htb` impersonating `Administrator`.
Because the SPN is now registered on `DC01$`, the KDC issues a ticket encrypted with `DC01$`'s secret key.
Fourth, because the service name is not protected within the encrypted part of the ticket (or via S4U2Proxy service substitution), the attacker can alter the requested service class to `cifs/DC01.pirate.htb` using `-altservice`, obtaining full administrative access to the Domain Controller.

## Mitigations

**Remediate Pre-Windows 2000 Computer Accounts:** Audit Active Directory for computer accounts configured with pre-Windows 2000 compatibility or `userAccountControl` flag 4128, which assign predictable default passwords matching their lowercase machine names. Ensure all such accounts have complex passwords assigned and remove legacy computer accounts from the Pre-Windows 2000 Compatible Access group.

**Audit and Purge Stale Pre-Staged Computer Accounts:** Periodically review the directory for pre-staged computer accounts that were created in advance but never had real physical or virtual machines joined to them. Remove stale pre-staged accounts that lack operating system metadata and logon activity to reduce unnecessary attack surface in the domain.

**Restrict Group Managed Service Account Retrieval:** Review the `msDS-GroupMSAMembership` attribute on all gMSAs to ensure only explicitly authorized host computers can retrieve managed passwords. Remove broad groups like `Domain Secure Servers` from accessing sensitive administrative gMSAs. Restrict membership in `Remote Management Users` to minimize unauthorized remote WinRM sessions.

**Enforce LDAP Signing and Channel Binding:** Enable LDAP server signing requirements and configure Extended Protection for Authentication (channel binding) on all Domain Controllers. Enforcing LDAP signing blocks NTLM relay attacks against LDAP and LDAPS by rejecting unsigned authentication tokens forwarded by intermediary proxies.

**Disable WebClient Service and WebDAV:** Disable the WebClient service via Group Policy across all domain workstations and servers where WebDAV functionality is not strictly required. Restricting WebClient eliminates HTTP-based authentication coercion vectors like MS-EFSRPC and MS-RPRN, preventing attackers from relaying coerced machine credentials to LDAP.

**Clean Up LSA Secrets and Stored Passwords:** Audit domain endpoints for plaintext passwords stored in the LSA secrets cache, registry autologon keys, and Credential Manager vaults. Enforce least-privilege administrative tiering to prevent privileged users from logging into lower-tier servers where their credentials can be dumped from memory or registry hives.

**Restrict SPN Modification and Audit Delegation Rights:** Remove `WriteSPN` (write permission on the `servicePrincipalName` attribute) from non-administrative users and groups over computer objects, especially Domain Controllers. Restrict `SeEnableDelegation` privilege and regularly audit accounts configured with Constrained Delegation to verify target SPNs remain tightly bound to their intended services.
