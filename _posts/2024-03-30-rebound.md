## Executive Summary

Rebound is an Insane-rated Windows Active Directory HackTheBox machine that demonstrates a realistic, long-form credential-chaining attack. No single vulnerability grants domain compromise; instead, several low-to-medium severity misconfigurations are chained together across multiple privilege tiers to achieve complete domain control.

The attack path proceeds as follows:

1. **Extended RID Brute Force (User Enumeration)** — With no initial domain credentials and anonymous access restricted, an extended RID cycling brute-force scan enumerates a list of valid domain users.
2. **AS-REP Roasting & Credential-less Kerberoasting (`oorend` & `ldap_monitor`)** — Testing enumerated users reveals that `oorend` has Kerberos pre-authentication disabled (`DONT_REQ_PREAUTH`). This lack of pre-authentication is abused with an Impacket fork (`-no-preauth`) to perform credential-less Kerberoasting against domain Service Principal Names (SPNs), capturing a TGS ticket for the `ldap_monitor` service account. Offline password cracking reveals `ldap_monitor`'s password (`1GR8t@$$4u`).
3. **Password Spraying (`oorend`)** — Performing a domain password spray with `1GR8t@$$4u` reveals password reuse on the standard domain user account `oorend`.
4. **Group Management & Shadow Credentials (`winrm_svc`)** — Enumerating domain access controls shows `oorend` can add members to the `ServiceMgmt` group. Adding `oorend` to this group grants `FullControl` over the Service Users Organizational Unit (OU). This administrative privilege over the OU is abused via a Shadow Credentials attack against `winrm_svc`: using `certipy shadow`, a key credential link (`msDS-KeyCredentialLink`) is injected to extract `winrm_svc`'s NT hash and obtain a WinRM shell.
5. **Active Session Abuse & Cross-Session Relay (`tbrady`)** — Once inside the target as `winrm_svc`, checking active user sessions reveals that domain admin-tier user `tbrady` is actively logged in. Using `RemotePotato0`, a cross-session NTLM relay attack forces `tbrady`'s session to authenticate against an attacker-controlled listener, capturing `tbrady`'s NTLMv2 hash, which is cracked offline (`2geth3r@123`).
6. **gMSA Password Extraction (`delegator$`)** — With `tbrady`'s credentials, domain enumeration reveals that `tbrady` has privileges to read the managed password of the Group Managed Service Account (gMSA) `delegator$`. Using `gMSADumper`, `delegator$`'s NT hash is extracted.
7. **RBCD & Double-Hop Delegation Abuse (Domain Admin)** — Domain delegation analysis shows that the computer account `DC01$` has Unconstrained Delegation, while `delegator$` is configured with Constrained Delegation to `http/dc01.rebound.htb` without Protocol Transition. To bypass the protocol transition restriction, Resource-Based Constrained Delegation (RBCD) is configured from `ldap_monitor` to `delegator$`. Using this setup, an S4U2Self/S4U2Proxy Kerberos double-hop delegation chain is executed to obtain a forwardable service ticket for `DC01$`. This privileged ticket is used to execute a DCSync attack, dumping the domain `Administrator` NT hash and achieving full domain compromise.

**Impact:** Complete compromise of the `rebound.htb` Active Directory domain and the domain controller (`DC01.rebound.htb`). All domain user hashes and secrets are accessible via DCSync.

**Machine Information**

Please allow up to 7 minutes for services to start. You will start the Rebound box with no initial credentials — enumeration must begin from an unauthenticated network perspective.

### DNS Resolution

Active Directory is fundamentally DNS-dependent — Kerberos service tickets are bound to specific hostnames (SPNs), and LDAP/SMB session setup relies on being able to resolve the domain and DC name correctly. Without this, tools like Impacket (`-k`), bloodhound-python, and certipy fail with confusing, seemingly unrelated errors.

```bash
kali@kali$ echo "10.129.232.31 rebound.htb dc01.rebound.htb dc01" | sudo tee -a /etc/hosts
```

## Exploitation

### AS-REP Roasting

**Concept:** Kerberos pre-authentication normally requires a client to first prove it knows the account's password (by encrypting a timestamp with a key derived from that password) before the KDC issues a TGT. Some accounts have the `DONT_REQUIRE_PREAUTH` flag set — either intentionally for legacy compatibility, or by mistake — which lets *anyone* request a TGT for that account with zero credentials. The response is encrypted with the account's password-derived key, so it can be cracked entirely offline with no lockout risk.

### Kerberoasting Without Credentials

**Concept:** Kerberoasting normally targets accounts with a Service Principal Name (SPN) set — any authenticated domain user can request a Ticket Granting Service (TGS) ticket for such an account, and that ticket is encrypted with the *service account's own* password hash rather than the requester's, making it crackable offline. Normally this requires at least one valid login first. A special forked version of Impacket supporting `-no-preauth` uses jjones's lack of pre-authentication to bootstrap this process — requesting Kerberoastable tickets for *other* SPN-holding accounts without ever needing jjones's actual password.

### Using Impacket Fork with `-no-preauth`


## Privilege Escalation

### Cross-Session Relay to tbrady

**Concept:** Windows allows COM (Component Object Model) objects to be activated across different logged-in sessions on the same machine. Certain CLSIDs, when activated, cause the target session's user context to authenticate outward on behalf of that activation. Tools like RunasCs (to execute locally as another user context) combined with a KrbRelay-style relay abuse this to trick another logged-in user's session into authenticating to a listener the attacker controls, capturing that user's NTLM challenge-response hash — without ever touching their session directly.

### Reading GMSA Password

**Concept:** Group Managed Service Accounts (gMSAs) don't have a human-set password — the Domain Controller automatically generates and rotates a long, random password, stored in the `msDS-ManagedPassword` LDAP attribute. Any principal explicitly listed in the gMSA's `PrincipalsAllowedToRetrieveManagedPassword` property can read this attribute directly via a standard LDAP query — no cracking, no exploitation of a bug, just a permitted read of a sensitive attribute that was granted too broadly.

### Delegation Abuse — RBCD Attack

**Concept:** Kerberos delegation lets a front-end service act on behalf of a user when talking to a back-end service. Resource-Based Constrained Delegation (RBCD) flips the traditional model: instead of the front-end account's admin controlling what it can delegate to, the back-end/target account decides who is trusted to impersonate users when contacting it, via the `msDS-AllowedToActOnBehalfOfOtherIdentity` attribute. Any account is always allowed to write this attribute about itself — this is by design, so a service owner can grant delegation rights without needing Domain Admin.

### Understanding Delegation Configuration

```bash
kali@kali$ findDelegation.py rebound.htb/oorend:'1GR8t@$$4u' -dc-ip 10.129.232.31
Impacket (Exegol fork) v0.14.0.dev0+20260623.162750.a2296a07 - Copyright Fortra, LLC and its affiliated companies 

AccountName  AccountType                          DelegationType                       DelegationRightsTo     SPN Exists 
-----------  -----------------------------------  -----------------------------------  ---------------------  ----------
DC01$        Computer                             Unconstrained                        N/A                    Yes        
delegator$   ms-DS-Group-Managed-Service-Account  Constrained w/o Protocol Transition  http/dc01.rebound.htb  No         
```

**Key Findings:**
- `DC01$` has **Unconstrained Delegation** — extremely dangerous
- `delegator$` has **Constrained Delegation without Protocol Transition** — S4U2Self tickets are NOT forwardable by the simple/direct method, since Kerberos-only delegation blocks the KDC from letting an arbitrary user's S4U2Self ticket carry the forwardable flag

### Set RBCD from ldap_monitor to delegator$

Since `delegator$`'s own credentials are now known, it's possible to authenticate *as* `delegator$` and write its own `msDS-AllowedToActOnBehalfOfOtherIdentity` attribute — granting `ldap_monitor` (already fully controlled, with a usable SPN) the right to impersonate any user when authenticating to `delegator$`. This bypasses the "Kerberos-only" restriction, because that restriction only governs what `delegator$` can delegate *outward* — it says nothing about who's trusted to delegate *inward* to it.

```bash
kali@kali$ rbcd.py rebound.htb/delegator\$ -hashes :696b4aac5199179d5d20fb8755676777 -delegate-from ldap_monitor -delegate-to delegator$ -action write -dc-ip 10.129.232.31 -use-ldaps
```

### The Double-Hop S4U2Proxy Chain

**Concept:** RBCD trust alone isn't enough — the Kerberos S4U extensions still need to be walked through properly. S4U2Self lets a service request a ticket to itself, on behalf of an arbitrary user, without that user's password; because of the RBCD trust just configured, the resulting ticket is forwardable. S4U2Proxy then takes that forwardable ticket and exchanges it for a ticket to a *different* service. Two hops are needed here because the RBCD trust only applies when the target of the S4U2Proxy request is `delegator$` itself — but the desired final destination is `http/dc01.rebound.htb`, which is what `delegator$`'s own separate delegation configuration allows it to reach.

### Get Forwardable Ticket from ldap_monitor

```bash
kali@kali$ getST.py rebound.htb/ldap_monitor:'1GR8t@$$4u' -spn browser/dc01.rebound.htb -impersonate DC01$ -self
```

**What Happens:** `ldap_monitor` performs S4U2Self (gets a ticket for itself as DC01$). Because of RBCD, this ticket is **forwardable**, saved as `DC01$@ldap_monitor@REBOUND.HTB.ccache`.

### Use Forwardable Ticket with delegator$

The `-additional-ticket` flag is what makes this a chained attack rather than a fresh request — it feeds the forwardable ticket from Step 13.1 in as the "already impersonating" input, letting `delegator$`'s real delegation target (`http/dc01.rebound.htb`) be reached, bypassing the "without protocol transition" restriction.

```bash
kali@kali$ getST.py rebound.htb/delegator\$ -hashes :696b4aac5199179d5d20fb8755676777 -spn http/dc01.rebound.htb -additional-ticket DC01\$@ldap_monitor@REBOUND.HTB.ccache -impersonate DC01$ -k -no-pass
```

**Result:** `DC01$@http_dc01.rebound.htb@REBOUND.HTB.ccache` — a ticket for the Domain Controller.

### DCSync & Domain Compromise

**Concept:** DCSync abuses the legitimate AD replication protocol (`DRSUAPI`/`DRSGetNCChanges`) that real Domain Controllers use to stay synchronized with each other. Any principal holding `Replicating Directory Changes` and `Replicating Directory Changes All` rights — normally only Domain Admins, Enterprise Admins, and DCs themselves — can request any account's password data this way. Since the forged ticket claims to be `DC01$` (an actual DC), the real DC has no reason to refuse.

## Mitigations

- **AS-REP Roastable user (jjones)**: Disable UF_DONT_REQUIRE_PREAUTH for all users
- **Weak password on ldap_monitor**: Enforce strong password policy
- **Password reuse (ldap_monitor = oorend)**: Use unique passwords for all accounts
- **oorend has Self right on ServiceMgmt**: Review and restrict group membership rights
- **ServiceMgmt has FullControl over Service Users OU**: Restrict permissions on sensitive OUs
- **Shadow Credentials attack on winrm_svc**: Monitor msDS-KeyCredentialLink modifications
- **Cross-session relay (RemotePotato0)**: Restrict COM cross-session activation
- **GMSA password readable by tbrady**: Restrict ReadGMSAPassword permissions
- **RBCD allows impersonation**: Monitor msDS-AllowedToActOnBehalfOfOtherIdentity
- **DCSync performed with HTTP ticket**: Restrict DCSync to only necessary accounts
- **Unconstrained delegation on DC01$**: Review and remove unnecessary delegation
